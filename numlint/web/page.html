Spell-checkers read your words. Nothing reads your numbers. numlint parses every quantity in a document — 8.5 km, £4.2m, two-thirds, Tuesday, 5 March 2026 — works out how they relate, and reports the ones that cannot all be true at once. No data, no network, no model: it checks a document against itself. Everything below runs in this tab.

Every number is an interval

Writing 8.5 km asserts a true value somewhere in 8.45–8.55. Writing 8 km asserts 7.5–8.5. Writing about 5 million asserts something much vaguer, and more than 500 asserts a lower bound and nothing else.

numlint reads that precision off the page — decimal places, scale words, hedges like roughly, nearly, at least — and turns every quantity into an interval. A finding is raised only when the interval a number states cannot overlap the interval its neighbours imply. That is what keeps it quiet: rounding is not an error, and 41% + 33% + 27% = 101% is not an error. What it flags is arithmetic that cannot be right as written — and it shows the working every time.

Tested on prose nobody wrote for it

The number that matters for a linter is how often it is wrong. Run over 6,503 published documents — 31 MB, 110,747 quantities spanning 1789 to 2006, numlint raised two findings in total. Both are genuine errors that have sat uncorrected in the Reuters archive since 1987: correspondents converting kilometres to miles with a factor of 0.6 instead of 0.621.

Everywhere a document gets written

A CLI, a zero-dependency library, SARIF output for CI annotations, and an MCP server — so a model can check its own arithmetic before it hands you the document. Models are markedly worse at arithmetic embedded in prose than at arithmetic in isolation, and re-reading their own numbers is not a reliable check on them.

# a file, a folder, or a pipe
npx numlint report.md
cat draft.txt | npx numlint

# annotations on every pull request
npx numlint --sarif docs/**/*.md > numlint.sarif

# let a model check its own arithmetic
claude mcp add numlint -- npx numlint-mcp
