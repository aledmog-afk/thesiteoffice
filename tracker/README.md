# Site Tracker

A small internal app for logging **weekly reports** and **snagging sheets** per site, and sending them to your main contractor. Lives at `/tracker/` on this site. Plain HTML/JS, no build step — same as the rest of this repo — backed by [Supabase](https://supabase.com) for login, the database, and photo storage.

## What it does

- **Organisation** — every user belongs to one organisation, and every site belongs to one organisation; a user can only ever see or touch sites in their own organisation, enforced at the database level (not just hidden in the UI). This happens automatically — the first time you create a site, an organisation is created for you behind the scenes (named after your email until you rename it), and you're its admin. Accepting an invite link to someone else's site also makes you a member of that site's organisation. There's no organisation-switcher yet — this app assumes one organisation per user, which is expanded on further as the roadmap continues. Rename your organisation any time in **Settings**.
- **Actions** — a per-site accountability tool: raise an action (a title, optional description, priority, due date), assign it to an owner (any editor — owner or collaborator — on that site), and track it through Open → In Progress/Blocked → Completed (or Cancelled). Every project has its own Actions tile/page; the default view shows only active work (Open/In Progress/Blocked), with a filter to see everything including completed and cancelled. Same editor-only access as Quality Gates/Commercials/Handover Documents — snagging-only members don't see this module. This is a first-class, reusable foundation, not tied to any one feature — future modules (defects, quality-gate failures, commercial issues) can generate Actions later without changing this engine.
- **Inspections** — a separate, ad-hoc inspection workflow from H&S Audits (see below): log an inspection (title, type — Quality/Health & Safety/Progress/Handover/General, date, inspector), then record structured **findings** as you walk the site (title, description, severity Low→Critical, evidence photos). A finding that needs following up gets **Create Action**, which raises a real entry in Actions (see below) — pre-filled from the finding, but you set the owner, priority and due date — and links back to it; the finding moves to Action Required automatically as a direct result of that click, never on its own. A finding that's actually a physical defect can instead (or as well) get **Create Snag**, which raises it onto the site's own snagging system (see below), linked back the same way — you decide which findings are genuine defects and which aren't; nothing here does that automatically. Once the work is actually done, mark the finding **Resolved** yourself — completing the linked Action never does this for you, since only a person can confirm a finding is genuinely closed out. Each site has its own Inspections tile showing how many findings are still open. Same editor-only access as Actions/Quality Gates/Commercials — snagging-only members don't see this module.
- **Dashboard** — "What requires my attention right now?" Your Dashboard (the sign-in landing page) now leads with a Control Summary above the site tiles: totals across every site you can access (open/overdue/due-today/blocked/high-critical actions, and how many sites need attention), an **Actions Requiring Attention** list (overdue, due today, due within 7 days, blocked, or high/critical priority — click through to the site or its Actions page), and a **Project Control List** sorted Attention-first, then Watch, then On Track — each with a plain-English reason ("Attention — 2 overdue actions (1 critical), 1 blocked."), never a numeric score. Filter either list (All/Attention/Watch/On Track for sites; All/Overdue/Due Today/Due Soon/Blocked/High-Critical for actions), or hit **↻ Refresh** any time. The same Control Summary appears on each individual site's own page, scoped to just that site. This is built entirely from your existing Actions (see below) plus unresolved high-severity H&S issues and inspection findings — it never invents a metric the data can't support, and a genuinely failed query always shows as a real error with a Retry button, never as misleading zeros.
- **Audit trail** — every change to a project, its members, quality gates, handover documents, the commercial ledger, snag items, weekly reports, actions, and organisation settings (name/logo) is recorded automatically at the database level — who changed it, when, and the before/after values — regardless of whether it happened through this app or a direct API call. This is infrastructure for later features, not a UI yet; there's no history screen to view it from today. See `sql/schema.sql`'s "v28 ADDITIONS" section and `tests/security/audit_log.test.mjs` for the full design.
- **Password reset** — "Forgot password?" on the sign-in page emails a one-time reset link (Supabase Auth's own flow); the same message shows whether or not the address has an account, so it can't be used to check who's signed up. The link opens **Reset Password**, where you set a new one.
- **File uploads** — capped at 50MB, and restricted to image, PDF, and common office-document types (specification documents accept the widest range, since a spec can reasonably be a Word doc, spreadsheet, or plain text file as well as a PDF). Enforced by Supabase Storage itself, not just the upload form — a file outside either limit is rejected before it's written, no matter what sent it. Who can upload where is enforced the same organisation/project-aware way as everything else in this app: your access to a specific site's photos, drawings, or documents is checked from the database, never assumed from a URL you were given.
- **Sites** — one entry per project (address, contract ref, main contractor name/email, contract start/completion dates, Employer's Agent, Clerk of Works, Site Manager, status). These appointment names/dates show on every weekly and monthly report's letterhead alongside the main contractor.
- **Company logo** — set once in **Settings**, it appears on every printed weekly report and snag list for every site in your organisation (not shared with other organisations).
- **Weekly reports** — a client-side Clerk of Works compliance record: programme status plus free-text **Comments on Programme**, a day-by-day weather tracker (see below), a **Verified Quality & Works Audit** table (each progress line has a plot/unit, a build-stage trade/work package, a contractor %, and a Clerk of Works quality verification note, e.g. "Pre-plaster check signed off"), a **Labour & Site Resource Tracker** (trade, headcount, activity/location, resource adequacy), H&S notes, a **Risk & Delays Tracker** (description, action required, owner, target date, an impact traffic light), a **Statutory & Testing Milestones** log (air permeability/sound/drainage pressure tests, Building Control/NHBC/Premier inspections and sign-offs), **Site Housekeeping** (conditions/cleanliness/access and egress), **Drawings / Information Received on Site**, a **Visitors** log, commercial items raised that week (see below), a "plan for next week" list, a general "other comments" field, and a tagged **photo gallery** — every photo carries a plot/area, an inspection category/element, a compliance status badge (Approved / Compliant, Action Required, Info Only), and a caption. A new report defaults "Week starting" to this week's Monday and "Week ending" to that same week's Friday, matching the Mon-Fri working week the weather tracker already uses — both are ordinary date fields you can still adjust by hand. The printed report shows a **Week No.** (this report's ordinal position among the site's reports, computed on the fly rather than stored) alongside the site's Clerk of Works/Site Manager/Employer's Agent and contract period. Every report has a clean printable view, with photo cards and table rows kept from splitting across a page break in the PDF. Every report also now goes through a **Draft → Reviewed → Approved → Issued** workflow, and its own **System Position** — see "Weekly Report System Position" below.
- **Weekly Report System Position** — alongside all the human-entered content above, every weekly report now has a system-generated **position**: an Attention/Watch/On Track exceptions summary (overdue Actions, blocked Actions, overdue high-priority Snags, critical Inspection Findings, unresolved high-severity H&S issues — exactly the same transparent rules the Project Control Dashboard uses, never a numeric score), a concise **"what changed this period"** list (Actions created/completed, Snags raised/closed/verified, Findings resolved, Inspections completed — built only from real timestamps, never a raw audit-log dump), and per-module summaries for Actions/Snags/Inspections/H&S with links back to the real records. Hit **↻ Refresh Position** on the report form any time to pull the latest position — it's never silently recomputed behind your back. The workflow is **Draft → Reviewed → Approved → Issued** (with **Revise** as the one way back to Draft from any later stage): while Draft or Reviewed, the whole report (human content and system position alike) stays fully editable; the moment it's Approved or Issued, its content is locked — Revise it first if something needs correcting. The system position is exactly that: a system-generated draft for you to check and adjust the human commentary around, never something issued to your contractor automatically.
- **Weather tracker** — a 7-day grid (Saturday and Sunday immediately before the report's week, then Monday–Friday of the week itself — the same order the paper Clerk of Works report used, built automatically from "Week starting") for logging condition and lost time per day, plus notes, with a live-computed total. The condition dropdown is Dry, Light Rain, Heavy Rain, Snow / Ice — leaving a day blank still means nothing to report; Dry is there for when you want a day explicitly on record as checked and clear, not because every day needs a condition set. The old single "weather" line is kept as an optional "Weather Notes" field for anything that doesn't belong to one specific day. Shown on the printed weekly report as a full day-by-day table, and rolled up into the monthly report as a month total plus a breakdown of just the days that lost time.
- **Weather auto-fill** — if a site has a postcode set (Site Details → Edit), the weather tracker looks up real weather for that location and pre-fills each day's condition automatically (using [Open-Meteo](https://open-meteo.com), free and keyless) — only days with rain or snow get filled in, so you just add lost hours and notes where they matter. It never overwrites a day you've already set, and quietly does nothing if the postcode isn't geocodable or the lookup fails — auto-fill is a convenience, never a requirement. The postcode is geocoded once (via [postcodes.io](https://postcodes.io), also free and keyless) and the coordinates cached on the site, so it's only looked up again if you change the postcode.
- **Build milestone tagging** — each progress/next-week line can be tagged with a build stage from a fixed dropdown (Site Set-Up, Groundworks, Foundations, Drainage, Slab Pour, Timber Frame, Superstructure, Scaffold Erect, Roofing, Windows & Doors, Scaffold Drop, Render, Cladding, 1st Fix split by trade — Carpentry, Electrical, Plumbing & Heating, Gas — Plastering, 2nd Fix split by trade — Carpentry, Electrical, Plumbing & Heating — Kitchen Fit, Bathroom Fit, Painting & Decorating, Flooring, Solar Panels, External Works, Testing & Commissioning, Snagging, Handover/PC) — or pick "Other" to type your own. The item text itself is optional once a milestone is set, so a line can just be "1st Fix – Electrical" with a % complete. The milestone list lives in `BUILD_MILESTONES` in `tracker/js/app.js` if you want to add/reorder stages.
- **Plot tagging on weekly reports** — the plot field on each progress/next-week line is a multi-select of the site's actual plots and apartment blocks, not freetext, so a line can be tagged to one or several at once (e.g. logging "1st Fix – Electrical" against Plot 3 and Plot 4 in one line, or "Frame Erect" against a whole block in another). Editing an older item that was tagged before this existed keeps its original freetext plot name(s) selectable too, so nothing gets silently dropped. The picker also always offers **External / Engineering Works** as a permanent, site-wide option alongside the plots and blocks — tag milestone items to it the same way, then use **Suggest from Milestones** next to the External / Engineering Works % field on Site Details to pull a starting-point % from whatever's been logged against it (same "fills the box, you hit Save" behaviour as a plot's or block's own Suggest button — never auto-overwrites). Milestones tagged to a block feed its own Suggest from Milestones on the block's page, same as a plot's.
- **Weekly reports auto-advance Plot Handovers** — for standalone houses (not flats or apartment blocks yet), once every milestone that makes up one of a plot's 4 quality gates has been logged at 100% against that plot across its weekly reports (deduped the same way as "Suggest from Milestones" — highest % ever reached, regardless of which report it was logged in), that gate's status automatically moves to **Under Review** — e.g. all four 1st Fix trades plus Plastering complete moves Pre-Plaster/First Fix to Under Review. It only ever moves a gate forward from Not Started/In Progress, and only ever as far as Under Review — a gate that's already Under Review, Approved, or marked N/A is never touched, and nothing here ever sets Approved itself, which always stays a person's decision on the plot's own page. The milestone groupings live in `GATE_MILESTONES` in `tracker/js/app.js`.
- **Week-to-week progress carry-forward** — starting a new report pre-fills "Progress this week" from the *previous* report's "Plan for next week", each line **starting at last week's own % complete** rather than resetting to 0 — you can see at a glance where each item left off and just update it if it's moved on (you can still add fresh items too). Anything left under 100% automatically rolls into that week's own "Plan for next week", carrying its % forward the same way, so it shows up again next time already showing where it stands — no manual re-typing, and no need to remember last week's figure. Hit 100% and it drops off for good.
- **Monthly reports** — on the Monthly Reports page, pick a month and hit "Generate Report" to roll every weekly report from that calendar month into one saved, printable summary: total weather lost time for the month plus a day-by-day breakdown, progress by milestone (deduped by item, so a milestone tracked across several weeks shows up once with its highest % reached — and still shows as completed even if it dropped off the weekly list after hitting 100%), outstanding items going into next month, H&S notes and issues/risks per week, that month's H&S Audit(s) (see below), commercial items raised that month with totals by type, snags raised/closed that month, a **Plot Handovers Completed This Month** list (see below), and a combined photo gallery. Generated reports are saved snapshots — editing a weekly report afterwards won't change a month you've already generated; delete and regenerate if you need to pick up changes.
- **Plot Handovers Completed This Month** — a plot is stamped fully handed over the moment its last quality gate and last handover document both reach Approved (N/A gates don't block it, same rule as everywhere else) — this happens automatically in the background while working on Plot Handovers, no extra step needed. The monthly report lists only the plots that reached that point *during that specific month*, with the date each one completed — not a running snapshot of every plot's current status, which used to make the section long and repeat the same "fully approved" rows every month regardless of what actually happened that month. A month where nothing was handed over simply leaves the section out of the report entirely.
- **Snagging** — organised **per plot**, using the same `plots` you add on Plot Handovers. Each plot gets exactly one snag list, created automatically the moment the plot is added; click into a plot to add as many items to it as you like (location, description, trade, priority, photo — each editable and deletable), then export that plot's list as a PDF. Each item's status is **Open**, **Closed**, or **Rejected** (for one the contractor disputes), plus an independent **⚠️ Flag Delay** for anything stuck waiting on something, with a reason — a flagged snag stays Open until it's actually closed or the flag's cleared, it's not a status of its own. "Raised by" has been dropped from the item form to keep it quick to fill in on site. Each item can also be given an **owner** (any project member, including snagging-only), a **due date**, and turned into a real follow-up **Action** with one click ("Create Action") when it needs formal tracking beyond the snag list itself — see "Snags, owners, due dates and verification" below. See "Snagging-only access" below for inviting someone who should only be able to work with snags.
- **Snags, owners, due dates and verification** — a snag can be assigned to anyone on the project (any role, including snagging-only — closing out snags is exactly their job) and given a due date, shown with the same overdue/due-today/due-soon badges as Actions. When a snag needs more than the snag list itself can track — formal ownership with an audit trail, a priority, something the Dashboard should surface — hit **Create Action** on it to raise a real entry in Actions (pre-filled from the snag, you set the title/priority/due date), linked back to the snag; the snag's own status is untouched by this, it isn't a second task system, just an optional escalation. Closing a snag (an owner or the contractor saying it's fixed) is different from **verifying** it — a separate, editor-only (owner/collaborator, not snagging-only) confirmation step that only becomes available once a snag is closed, for the "contractor says it's done, client independently checks" workflow real snagging follows; reopening a verified snag always clears the verification automatically, since it's no longer true. Every change is in the audit trail (see below) same as everything else.
- **General / Site Visit snag lists** — for a walk-round that isn't about one plot (touring several plots in one go, or logging a site-wide/external issue), hit **+ General List** on the Snagging page instead of clicking into a plot. Name it whatever you like (defaults to "Site Walk - [today's date]") and it gets its own card in a separate "General / Site Visit Lists" section above the plots table. Each item you add to a general list carries its **own Plot** dropdown (any plot on the site, or "External / Site-wide" for something that isn't tied to one) — everything else about the item (location, description, trade, photo, status, delay flag) works exactly the same as a plot-specific snag. You can create as many general lists as you like. These stay deliberately separate from the per-plot Open/Closed/Rejected counts on the Snagging page and from the monthly report's plot handovers snapshot — a general list's items aren't rolled into either. A general list you no longer need can be removed entirely with the **Delete List** button on its own page (deletes every item in it too). Plot-specific snag lists don't get this button — they're tied one-to-one with their plot, so deleting one is done from the Plot Handovers page by deleting the plot itself.
- **Site Snag Sheet** — hit **📄 Site Snag Sheet** on the Snagging page to generate one combined, printable list of every snag across the whole site — every plot's list and every general list, in one document — rather than exporting each list separately. Defaults to **Open only**; a dropdown on the page (not printed) switches to Open with flagged items sorted first, All, Closed only, or Rejected only, re-rendering instantly with no reload. Rows are grouped by plot (in natural plot order — Plot 2 before Plot 10) with general-list items after, sorted alphabetically by list title; a summary line always shows the full site's Open/Flagged/Closed/Rejected counts regardless of which filter is currently shown. Same Print/Save as PDF and Email buttons as every other document in this app, with the PDF's suggested filename set from the site name, the active filter, and today's date.
- **Weekly report photos auto-raise snags** — tag a weekly report photo's compliance status as **Action Required** and it's automatically raised as a snag when you save the report — no separate trip to Snagging needed. The photo's Plot/Area tag is matched against the site's real plots the same digit-based way plot tags are matched everywhere else in this app (so "Plot 1" and "1" both resolve to the same plot); if it matches, the snag lands on that plot's own snag list (location = the photo's Inspection Category/Element, description = its caption, same photo attached). If it doesn't match a real plot — a typed-in area like "S278 Entrance", an apartment block's own name, or left blank — it lands on a shared general list called "Weekly Report Issues" instead (created once per site, reused every time), with the plot/area tag folded into the snag's location so the context isn't lost. A photo already raised shows a **✓ Snag Raised** badge (linking to the snag on the printed report); editing that same photo's tag/category/caption and saving again keeps the snag in sync — including moving it to the right plot's list if you go back and correct the tag — rather than freezing it wherever it first landed.
- **Sending to the contractor** — every report/snag list has a "Print / Save as PDF" button (uses your browser's print-to-PDF) and an "Email to Contractor" button that opens a pre-filled email to the contractor's saved address — attach the PDF you just saved. A weekly report's suggested filename is "Weekly Report - [Site Name] - [Week Ending as d.m.yy]" (e.g. "Weekly Report - Red Dragon - 21.8.26") — browsers use the page title as the default PDF filename, so this is set from the report's data before you print.
- **RAG status & plot-based progress** — set an overall Red/Amber/Green status and a planned/baseline progress % by hand (Site Details → Edit). Actual Progress is a *weighted* average: every standalone plot/flat's own progress % counts once (set directly on that plot's page, under Plot Handovers), every apartment block's own progress % (set on the block's page — see below) counts once **per flat in that block** — since a block's shared structure/civils underpin every flat sitting on top of it, a fully-built frame under 30 still-empty flats is genuine, substantial site progress, not something that should barely move the needle — and a site-wide **External / Engineering Works %** (Site Details → Edit, for civils/drainage/landscaping that isn't any one plot or block) counts once. A block with no flats yet counts as a single unit, same as a plot, so it isn't invisible in the average before any flats are added. Every one of those numbers is set by hand, so it's always correctable — nothing recalculates itself and silently overwrites a number you've typed. On a plot's or block's page, **Suggest from Milestones** will fill in a starting-point % computed from the build milestones logged against that plot/block (matched by name) across all its weekly reports (deduped, so a milestone logged in several weeks only counts once, at its highest % reached) — it only fills the box, you still have to hit Save. Shown as a badge and dual progress bar on the dashboard and site page, with a plain-English slippage line ("-5% Behind Programme" / "On Programme" / "+X% Ahead").
- **Internal Works Milestones** — a second, more granular layer of progress on each plot's own page, alongside its single Plot Progress % and its 4 Quality Gates: Timber Frame, Roof Covering, Carpentry First Fix, Electrical First Fix, Mechanical First Fix, Dry Lining, Plastering, Kitchen, Bathroom, Second Fix Carpentry, Second Fix Mechanical, Second Fix Electrical, Carpentry Finals, Decoration, Flooring, Mastic, Clean, Snagging (18 stages for a standalone plot, 16 for a flat — Timber Frame/Roof Covering are skipped there since that structural work already lives on the block's own gates). Every plot gets these automatically, same as its gates/documents. Each stage is its own 0-100%, editable directly on the plot's page, since real trade trackers record genuine partial completion (e.g. plastering 80% through a plot) rather than a single done/not-done flag. Deliberately independent of Plot Progress — nothing here is derived from or feeds back into it automatically; edit either without affecting the other. The stage list is shared across every site rather than customised per project — it started as the 16 stages one client's tracker used and grew to 18 (adding Carpentry Finals and Mastic) once a second site's tracker needed them; a future site needing yet another stage would grow it the same way.
- **Export Trackers** — hit **📊 Export Trackers** on the Plot Handovers page to generate an `.xlsx` straight from the site's live data: an **Overall Progress** sheet (every plot's and block's Plot Progress %, plus the site's Actual/Baseline/External Works % underneath) and an **Internal Works** sheet (one row per plot, one column per Internal Works Milestone stage — see below). The reverse direction of how those two spreadsheet styles originally got imported into this app. The Internal Works sheet's layout mirrors the client-supplied templates it was reverse-engineered from — a project title/generated-date header, a "Plots X-Y" label, then plot rows grouped under a plain-text section row per apartment block (the same role "Block 1-4" rows played in the originals), standalone plots listed first with no section row. A milestone stage a plot was never seeded with (Timber Frame/Roof Covering on a flat) is left blank, distinct from a genuine 0%. Uses [SheetJS](https://sheetjs.com), loaded on demand from esm.sh only when the button is clicked, same CDN-import approach the app already uses for the Supabase client.
- **Plot Handovers** — quality gates, statutory handover documents, and progress % are tracked **per plot**, not once for the whole site, since each house/unit goes through its own sign-off. Add a standalone house with **+ Plot**, or set a **Total Plots** target on Site Details and hit **Generate Missing Plots** there to bulk-create the rest in one go (named "Plot 1", "Plot 2", … skipping any that already exist by name, so re-running it later after adding more just fills the gap). Every standalone plot automatically gets its own 4 quality gates (Substructure & Drainage, Frame & Wind/Watertight, Pre-Plaster/First Fix, Pre-Handover/PC — each with a status, an N/A option for gates that don't apply to that plot, and a checklist that timestamps sign-off when ticked), 5 statutory documents (Building Control, air permeability/acoustic certs, electrical & gas certs, warranty cover note, O&M manuals — each with a status and a real file upload, stored in Supabase, not a mock), and its own snag list. Gates marked N/A are left out of "X / Y approved" counts entirely — on both sides of the fraction — so marking one N/A can only help a plot's ratio, never hold it back; a plot with everything else approved shows as fully complete. Total Plots is just a target count for the bulk-create action above — it has no effect on Actual Progress, which is always just the average of however many plots/blocks actually exist.
- **Apartment blocks** — for sites built as full apartment blocks rather than individual houses, add a block with **+ Block** instead of a plot. A block gets its own page with a **Block Progress** %, its own 4 shared quality gates (Substructure & Drainage, Frame & Superstructure, Roof & Building Envelope, Communal Areas/M&E/Fire Strategy) and 5 shared handover documents (Building Control, warranty cover note, fire strategy report, communal M&E pack, buildings insurance) — tracked **once for the whole block**, not duplicated per flat, since foundations/frame/roof/communal areas are single pieces of work regardless of how many flats sit on top of them. When you create a block you can optionally type its flats' actual plot numbers right away — a range like `23-30`, a comma list like `23,25,28`, or a mix of both — to bulk-create flats named exactly that (a block's flats are often numbered to continue the site's own numbering rather than restart at 1, so nothing forces a "Flat N" name onto them). Leave it blank to add flats one at a time with **+ Flat** on the block's page afterwards, which takes the same range/list input (or just a single number) any time — adding exactly one jumps straight to its page, adding several returns you to the block. Re-running either with numbers that already exist on that block just fills in whichever are missing. Each flat is a normal plot under the hood (so it shows up in Snagging and gets its own progress % and Suggest from Milestones the same as a house), but with a smaller, fit-out-focused set of gates (1st Fix, 2nd Fix, Kitchen & Bathroom Fit, Decoration/Flooring/Pre-Handover Snagging) and documents (air permeability/acoustic cert, electrical & gas certs, EPC, unit warranty cover note, O&M manuals) — the structural sign-offs live on the block instead. Deleting a block deletes all its flats (and their gates/documents/snags) along with it — you're warned before this happens. Plot Handovers lists standalone plots and blocks separately; a flat only ever appears under its block, not in the standalone plots list.
- **Commercials** — an early warning / proposed variation / instruction log per site, with cost and time impact, a status (pending/approved/rejected), and running totals for approved variations and pending exposure. You can log items directly on the Commercials page, or add them under "Commercial items this week" on a weekly report — those are pushed into the ledger automatically when the report is saved (a 📋 icon on the ledger links back to the report it came from). Editing an already-pushed item's title/type/cost/time on the report updates that same ledger entry; removing it from the report's own list never deletes the ledger entry — the ledger is the durable record once an item exists there.
- **H&S Audits** — a separate section per site, expected once a month. Hit **+ New Internal Audit** on the H&S Audits page to walk a fixed, condensed checklist (Statutory Documentation, General Requirements, Site Based Hazards, Environmental — the list lives in `HS_CHECKLIST` in `tracker/js/app.js`) — each item defaults to **Compliant** and you flip any exceptions to **Non-Compliant**, **N/A**, or **Good Practice**, with a note and an optional photo per item. Marking something **Non-Compliant** reveals a traffic-light **Severity** (Low/Medium/High, shown Green/Amber/Red) for how serious that particular issue is. A score % (excluding N/A items from both sides of the fraction, same rule as the quality-gates ratio) and a flagged count are shown on the audit and in the list. **+ Upload External Audit** logs a third-party audit (e.g. a SHE inspection PDF) instead — just a file and who conducted it, no checklist. Either type is logged against a calendar month (independent of the date you actually did it, so a late upload can still count for the month it covers) — if the current month doesn't have one yet, a **⚠️ No H&S audit logged this month** flag shows on the H&S Audits tile on the site page, and the monthly report carries the same flag for any month it rolls up with none. The monthly report also lists whichever audit(s) *did* happen that month, with their score/flagged count or file link.
- **Drawings & Layouts / Pinpoint Snagging** — upload an overall site layout (reference only) and per-plot floor plans. Click anywhere on a floor plan to drop a pin and raise a snag at that exact spot; existing pins are clickable and show the snag's details, status and photo. Pins are stored as a percentage of the image's width/height, so they land in the same spot on any screen size.
- **Bulk upload drawings** — hit **📁 Bulk Upload** on the Drawings page and select every drawing for the site at once, instead of the one-at-a-time form. Each file's plot is pre-guessed from its own filename (the same digit-based matching used everywhere else in the app, so "Plot 5 - Ground Floor.pdf" or "P5-GF.pdf" both guess Plot 5) and shown in an editable review list — fix any wrong guess, rename, or remove a file before hitting Upload All. Files upload one at a time; if one fails partway through (a bad connection, say), the ones that succeeded are already saved and only the failed file is left in the list to retry, rather than losing the whole batch. There's no revision/version tracking yet — a re-upload for a plot that already has a drawing just adds a second, independent one; that's a planned follow-up.
- **Specification** — a section on the Drawings page for a site's own reference paperwork (e.g. a spec per house type or trade), separate from the plot-specific floor plans above it. **+ Add Specification** takes a name and any file type (PDF, Word, Excel, image — whatever the document actually is); each one is listed with a link to open it and a Delete button. Unlike drawings, these are never plot-scoped and never support pinning — deliberately its own table (`specifications`) rather than a drawing with no plot set.
- **Documents** — a project-scoped **controlled document register** (drawings, specifications, or "other" project records), separate from Drawings & Layouts above and from every operational-evidence photo elsewhere in the app. Each document has a type, title, optional document number, a status (Draft/Current/Superseded/Archived), and a full **revision history**: uploading a file for a new document creates Revision 1 and makes it current; uploading again for an existing document always creates a brand-new revision — it never overwrites the file that's there. The previous revision is automatically marked superseded and the document repoints to the new one as current; nothing is ever silently replaced, and there's no way to accidentally overwrite the current file from the UI. The **Documents** page lists every document for the site (title, type, doc number, status, current revision, last updated, uploaded by), with filters by type/status; open one to see its full revision history, with Current and Superseded clearly marked, and Open/Download on every revision, not just the current one. Files live in a private storage bucket — unlike photos elsewhere in this app, a document's file isn't reachable by URL alone; access is checked against your real project membership every time. Read access is available to everyone on the project (including snagging-only members, matching their existing access to Drawings); creating a document or uploading a new revision is editor-only (owner/collaborator). There's no delete — retiring a document is done with **Archive**, which keeps every revision and its full history intact. Existing Drawings and Specifications are automatically included here too (migrated in behind the scenes, alongside the original Drawings page, which keeps working exactly as it always has for pinpoint snagging).
- **Bulk Export (Documents → Microsoft 365 / SharePoint)** — select any number of documents on the Documents page (or **Select All**, optionally after filtering by type/status) and hit **Export Selected (ZIP)** to download one ZIP built for dropping straight into a SharePoint/Teams document library or a synced OneDrive folder: a folder per document type (`01 Drawings`, `02 Specifications`, `03 Other Documents`), clean Windows/SharePoint-safe filenames (`[Doc Number] - [Title] - Rev [N].ext`, de-duplicated automatically if two would otherwise collide), and an `Export Manifest.csv` listing every file's project/title/type/number/revision/status/original filename/export filename/exported date. By default the export includes only each document's **current** revision — tick **Include revision history** to also export every superseded revision, organised into `Current/` and `Revision History/` subfolders per document. Built entirely client-side (there's no backend to generate it on your behalf) using the same authenticated access as the rest of the app, so an export can never include a document you couldn't otherwise open — and it's capped at 150MB per export (narrow your selection or filters if you hit this) rather than silently dropping files partway through.
- **Programme** — a project-scoped, deliberately minimal foundation for construction programme control: one **Programme** per project (Draft/Active/Archived — only one can be Active at a time), containing any number of **Activities** (a task or milestone, optionally tied to a plot) each carrying a genuinely three-way date model — **Planned** (what an external programme, e.g. Microsoft Project/Asta/Excel, says should happen), **Forecast** (what's currently expected — defaults to the planned dates until you say otherwise), and **Actual** (what really happened) — plus a status (Not Started/In Progress/Complete/Cancelled) and a % complete. Marking an activity Complete automatically sets its % to 100 and stamps its actual finish date (once, if you hadn't already set one) — reopening it afterwards never erases that real completion date. This is deliberately **not** a scheduling tool: this app is not trying to replace Microsoft Project/Asta/Primavera/Excel, which stay the actual place a programme gets planned — see "Programme Control design" below for the full architecture and what's intentionally not built yet (no Gantt chart, no dependency/critical-path engine, no programme versioning, no dashboard/weekly-report integration — those are all explicit future phases). The **Programme** page (editor-only — owner/collaborator, not snagging-only) is a practical table: create/edit/delete an activity, filter by status, sort by finish date/title/status. Activate a draft programme once you're ready to start tracking against it; Archive retires one without losing its activities.
- **Multiple accounts & collaboration** — each site has an **owner** (whoever created it) and any number of **collaborators**, who get full edit rights on that site's reports, plots, snags, gates, documents, commercials and drawings — same as the owner. Only the owner can delete the whole site or manage who has access. To bring someone else onto a site, open it and go to the **Collaborators** card → **Get Invite Link**, then send that link however you like (WhatsApp, email, Slack — there's no auto-send, same as everywhere else in this app). Whoever opens it while signed in (or signs up first, then is sent straight back to it) joins instantly — no approval step. **Regenerate** swaps in a fresh link, invalidating the old one; **Revoke** turns it off entirely. Anyone (owner or collaborator) can leave a site from that same card; only the owner can remove someone else. Your dashboard only ever shows sites you're the owner of or a collaborator on — creating a new site makes you its owner automatically. Accepting an invite also makes you a member of that site's organisation (see "Organisation" above) — the company logo (Settings) is shared across every site in that organisation, not per-site, but never crosses into a different organisation's sites.
- **Snagging-only access** — a third membership tier, for whoever actually closes out snags on site (e.g. the main contractor's site manager) but shouldn't see anything else. They can fully manage snag items — add/edit, upload photos, assign (including to themselves), set a due date, and set the status to **Open**, **Closed**, or **Rejected** (for a snag the contractor disputes is actually a defect), plus raise a **⚠️ Flag Delay** on any snag that's stuck waiting on something (with a reason), separately from its status — a flagged snag stays Open (still outstanding) until it's actually closed or the flag is cleared. The one thing they can't do is **verify** a closed snag — that's deliberately owner/collaborator-only, so the person closing a snag out is never also the one independently confirming it's actually fixed. They can't see weekly reports, quality gates, statutory documents, the commercial ledger, other drawings, monthly reports, apartment blocks, site details, or the collaborators list — enforced at the database level, not just hidden in the UI. The Collaborators card has a **second, separate invite link** just for this ("Get Snagging Invite Link") — send the right one to the right person, no extra step needed to downgrade anyone afterwards. Opening a site they only have snagging access to shows a cut-down page with nothing but a Snagging tile.

There's no login for the contractor — they only ever receive the PDF/email you send them.

## One-time setup

1. **Create a free Supabase project** at [supabase.com](https://supabase.com) (the free tier is more than enough for this).
2. In the Supabase dashboard, go to **SQL Editor → New query**, paste in the contents of [`sql/schema.sql`](../sql/schema.sql), and run it. This creates the tables, security policies, and the `site-photos` (public, for photos) and `controlled-documents` (private, for the Documents feature) storage buckets.
3. Go to **Project Settings → API** and copy the **Project URL** and the **`anon` public key**.
4. Open `tracker/js/config.js` and paste them in:
   ```js
   export const SUPABASE_URL = "https://xxxx.supabase.co";
   export const SUPABASE_ANON_KEY = "eyJ...";
   ```
   The anon key is safe to ship in client-side code — the SQL script's Row Level Security policies are what actually control access (any signed-in user can read/write; nobody else can).
5. Deploy as normal (this repo's Cloudflare Pages integration picks up static files automatically). Visit `/tracker/`.
6. On first visit, click **Create one** on the sign-in page to make your first account (yourself). Anyone else on your team can do the same — Supabase's default settings will email a confirmation link.

### Updating an existing project (schema changes)

`sql/schema.sql` is written to be safe to re-run in full any time it changes — every statement is `if not exists` / `create or replace` / `drop policy if exists`. If you already have a Supabase project set up, just paste the **whole current file** into SQL Editor and run it again to pick up new tables/columns; nothing existing gets dropped or overwritten destructively.

### Turning off "confirm your email" (optional)

By default Supabase requires clicking a confirmation link before a new account can sign in. For an internal team tool you may prefer to skip this: in the Supabase dashboard go to **Authentication → Providers → Email** and turn off "Confirm email". You can also just leave it on — it only adds one click the first time.

## Adding a team member

Have them sign up from the login page themselves (or Supabase → **Authentication → Users → Add user**). A new account starts with **no sites** — send them an invite link from the specific site(s) they need (Site page → Collaborators → Get Invite Link) to bring them onto it.

## Notes for future changes

- All data access goes through the Supabase JS client (`tracker/js/supabase-client.js`) using the anon key + Row Level Security — there's no custom backend/API to maintain.
- Photos are stored in the public `site-photos` bucket so they load in printed/PDF reports without needing auth headers. If snag/report photos ever need to be private, switch the bucket to private and swap `getPublicUrl` for `createSignedUrl` in `tracker/js/app.js`.
- Weekly report, snag, and handover photos are resized (max 1920px on the longest side) and re-encoded as JPEG at ~78% quality in the browser before upload (`compressImage`/`uploadImage` in `tracker/js/app.js`), to keep Supabase's free 1GB storage tier from filling up. A typical phone photo drops from 5–8MB to under 1.5MB. The company logo (Settings) is deliberately left uncompressed — it's a single file, and re-encoding could strip transparency from a PNG logo.
- Drawings (site layouts, plot floor plans) go through the same idea at higher settings for legibility — resized to max 2560px and re-encoded as WebP at ~75% quality (`compressDrawing`/`uploadDrawing` in `tracker/js/app.js`). Verified against a realistic 6.6MB/5000×3500 test scan: came out at 2560×1792 / 390KB. **PDF drawings are the one exception** — browsers have no built-in way to rasterise a PDF via the Canvas API, so PDF uploads are stored as-is, unconverted and uncompressed, and are view/download-only (no pinning). If you regularly upload PDF drawings and storage becomes a concern, export them as PNG/JPG before uploading, or ask for a PDF→image conversion step to be added (it would need a library like `pdf.js`, which is a much heavier addition).
- Quality gates already have `drawing_id`/`x_coordinate`/`y_coordinate` columns (for pinning a gate to a location on a drawing), but there's no UI wired up for it yet — only snags are pinnable today. The columns are there so that can be added later without another migration.
- Apartment blocks (`blocks` table) reuse the existing `quality_gates`/`handover_documents` tables rather than a parallel set of tables — both got a new nullable `block_id` alongside the (now nullable, previously required) `plot_id`, with a check constraint enforcing exactly one of the two is set per row. `plots.block_id` (nullable, `on delete cascade`) is what makes a plot a "flat" rather than a standalone house — `seed_plot_defaults()` branches on whether it's null to decide which gate/document set to seed. This was chosen over a separate `flats`/`block_gates` table structure specifically so `block-detail.html`'s gate-card and document-row rendering could reuse `plot-detail.html`'s code almost unchanged, just re-scoped to `block_id`.
- Quality gates and handover documents used to be one set per site; they're now one set per **plot** (`plots` table), created automatically whenever a plot is added. Any gates/documents that existed before this change were migrated into an auto-created "Plot 1" for their site during the schema migration, so nothing was lost — rename or re-organise that plot if it doesn't match how you actually want plots split up.
- Snag lists went through the same change: `plots` is now the single shared table behind both Plot Handovers and Snagging, and a snag list is created automatically alongside a plot's quality gates/handover docs (one list per plot, `snag_lists.plot_id`). Any pre-existing snag items from before plots existed were migrated into an auto-created "Plot 1" the same way. Deleting/renaming a plot is done from the Plot Handovers page — Snagging just links into whichever list already exists for the plot.
- Actually sending email automatically (rather than opening a pre-filled draft) would need an email-sending service (e.g. Resend) wired into a Netlify function with an API key — not set up here to keep the app dependency-free out of the box.
- The browser tab icon is a single hand-drawn `tracker/favicon.svg` (dark rounded square, amber location-pin) referenced from every page via `<link rel="icon" type="image/svg+xml">` — no PNG fallback, since SVG favicons are well supported by every modern browser this app targets.
- This app grew out of, and is meant to fully replace, a paper "Clerk of Works Weekly Report" template. Comparing the two directly turned up a few gaps that got closed in one pass: site-level appointment names (Employer's Agent, Clerk of Works, Site Manager) and a contract completion date on `projects`, plus Comments on Programme / Site Housekeeping / Drawings-Information Received / Visitors as free-text fields on `weekly_reports` — each rolled up into `monthly_reports` the same "one array entry per week that had something to say" way `health_safety_notes` already was. Two things from the paper form were deliberately **not** replicated: (1) its AM/PM-split weather grid with a separate temperature reading per half-day — the app's weather tracker stays one condition/lost-hours/notes entry per day (now extended to all 7 days, Sat–Fri, not just the working week) since it's live-auto-filled from Open-Meteo and doubling it to AM/PM would mean twice the manual entry for a live API that only sensibly fills one slot per day anyway; and (2) the paper form's running CVI's-to-date/AI's/Dayworks counters and a separate weekly labour-hours-lost figure — these were judged already covered, in more useful and filterable form, by the existing Commercials ledger (instructions/variations/early warnings) and Risk & Delays Tracker, so no duplicate fields were added for them.
- **Week No.** on the printed weekly report is computed at view time (a count of the site's reports with `week_starting` on or before this one), not a stored column — avoids it ever drifting out of sync if a report is later backdated or reports are generated out of order.
- Multi-account access control is enforced by Row Level Security, not client-side checks — every table's policies now check membership via a `project_members` table (through `is_project_member()`/`is_project_owner()` helper functions) instead of "any signed-in user," so even a hand-crafted API call can't reach a site you're not on. Membership is only ever granted two ways, both `security definer` so a client can't insert into `project_members` directly: automatically for whoever creates a site (a trigger), or via `join_project_by_invite()` when someone opens a valid invite link. `org_settings` (the company logo) and the `site-photos` storage bucket deliberately stay outside this — they're organisation-wide, not site-scoped, so every signed-in user keeps read/write on them same as before. **Storage isn't per-site restricted** — any signed-in user can still upload/delete under any project's photo folder if they somehow knew the path, same as before this feature; this was a deliberate scope decision, not an oversight, since reads on that bucket are already fully public (unauthenticated, keyed by an unguessable UUID filename) to support printed/PDF reports, so a member-only write policy would have added complexity without closing the read side's exposure. Tighten this later if it matters for your use case — the natural approach is `storage.foldername(name)` combined with `is_project_member()`, but the bucket has three different path shapes (`org-logo/…`, `<project_id>/…`, `drawings/<project_id>/…`) that would each need separate handling.
- When migrating an existing installation onto this feature, every user who could see a site before still can — they're added as either its owner (if `projects.created_by` matches them) or a collaborator (everyone else), once, the first time this migration runs. This is a one-time grandfather step, not an ongoing behaviour: a user who signs up afterwards does **not** get automatically added to old sites on a later `schema.sql` re-run, only to sites they create or are explicitly invited to.
- General (not-plot-specific) snag lists reuse `snag_lists.plot_id`, which was already nullable with a unique index that already tolerated multiple null rows (an artifact of the pre-migration legacy-list backfill mentioned above) — creating a second, third, etc. null-`plot_id` list on purpose needed no schema change there. The only new column is `snag_items.plot_id` (nullable, `references plots(id) on delete set null`), letting each item within a general list record its own plot independent of the list itself; deleting that plot later just clears the reference rather than deleting the snag item. No RLS changes were needed — the existing editor-only writes on `snag_lists` and fully member-level `snag_items` already produce the right permission shape (owner/collaborator creates the list, anyone including a snagging-only member can add/edit its items).
- Snagging-only is a third `project_members.role` value alongside `owner`/`collaborator`, with its own invite code column (`projects.snagging_invite_code`) and its own pair of `regenerate_snagging_invite_code()`/`revoke_snagging_invite_code()` functions — kept fully independent of the collaborator invite link so an owner never has to remember to "downgrade" someone who joined the wrong way. `is_project_editor()` (owner or collaborator, not snagging) gates every table a snagging-only member shouldn't see at all (weekly reports, quality gates, handover documents, commercial items, monthly reports, blocks, `project_members` itself, and writes to plots/drawings/snag_lists); `is_project_member()` (any role) still gates `snag_items` fully and read-only access to `plots`/`drawings`/`snag_lists`, since a snagging-only member needs those to navigate to and pin a snag. `get_my_role()` is a small security-definer function that lets a client find out its own role even on tables it otherwise can't read (`project_members` itself is editor-gated) — `project.html` uses it to decide whether to render the full site page or the cut-down snagging-only one.
- Weather auto-fill is the one place the app calls an external API directly from the browser rather than going through Supabase — `geocodePostcode`/`fetchWeatherConditions`/`conditionFromWeatherCode` in `tracker/js/app.js`. Both postcodes.io and Open-Meteo are free and keyless, so there's nothing to configure, but it does mean those two domains need to be reachable from wherever the app is used.
- H&S Audits are two tables: `hs_audits` (one row per audit, `audit_type` 'internal'/'external', gated `is_project_editor()` for every operation — this is a management feature, not exposed to snagging-only members at all) and `hs_audit_items` (one row per `HS_CHECKLIST` entry, internal audits only). `section`/`item_name` are copied onto each item as plain text at creation time rather than referencing `HS_CHECKLIST` by index, so editing that constant later never rewrites an already-completed audit's wording. `hs_audits.month` uses the same first-of-month `date` format as `monthly_reports.month`, so "does this project have an audit for month X" is one equality match; the "flag if not done this month" nudge on the site page and the monthly report roll-up both just check `month = <first of that month>` against today's/that report's month, live — there's no separate stored flag or historical "missed months" tracking, only "does the current (or that report's) month have one." A monthly report freezes a snapshot of that month's audits (score/flagged count for internal, file link for external) into its own `hs_audits` jsonb column at generation time, same convention as its other fields, so it doesn't change if an audit is edited or deleted afterwards.
- The weekly report's Clerk of Works upgrade added three new jsonb columns to `weekly_reports` — `labour_records`, `risk_items`, `statutory_milestones` — plus two fields folded into JSON shapes that already existed rather than getting columns of their own: `verification_notes` on each `progress_items` entry (Verified Quality & Works Audit) and `plot_area`/`category`/`compliance_status`/`caption` on each `photos` entry (the tagged photo gallery). The old free-text `issues_risks` column is left in place, unused by the form going forward — same "old column stays, unused" pattern as `progress_summary`/`next_week_plan`/`labour_on_site` before it — since `risk_items` replaces it as the form's structured input. Because the monthly report's "Issues / Risks / Delays" section previously only ever read that free-text field, `monthly_reports` gained its own `risk_items` jsonb column (flattened across the month's reports with each entry tagged by `week_starting`, same convention as `commercial_items`) so the monthly roll-up doesn't silently go blank once weekly reports stop populating the old field; `monthly-report-view.html` renders both — the new structured table for reports that have `risk_items`, and the legacy text section for any that only ever had `issues_risks`. `progress_items`' dedup (across a month's weekly reports, keyed by item id, keeping the highest % reached) now also carries the most recent non-blank `verification_notes` forward, so a Clerk of Works sign-off logged in an earlier week isn't lost if a later week re-logs the same item with a lower % or a blank note. Labour records and statutory milestones are **not** rolled up into the monthly report — they're kept as weekly-only, operational detail.
- `mountTableEditor()` in `tracker/js/app.js` is a small generic add/edit/delete table editor (columns: text/number/select/date, with optional badge coloring and `<datalist>` freetext suggestions) driving the Labour, Risk, and Statutory Milestones trackers on the weekly report form from one shared implementation rather than three near-duplicate ones. Every `select` column always gets an injected blank leading option even when the caller's `options` list doesn't include one — without it a `<select>` defaults to its first real option, which would make an "add a completely empty row" click silently pick up e.g. "Adequate" or "Low" instead of being ignored.
- Weekly report photos auto-raising snags needed no schema change at all — it's entirely client-side logic in `weekly-report-form.html` (`resolveSnagListId`/`syncActionRequiredSnags`) reusing the existing `snag_lists`/`snag_items` tables and RLS exactly as they already stood, plus two new keys (`snag_item_id`, `snag_list_id`) folded into each `photos` entry, the same "add fields to an existing jsonb shape" pattern used throughout this feature. Plot matching uses `normalisePlotToken()` (now exported from `tracker/js/app.js`) — the same digit-extraction matching `suggestPlotProgress()`/`syncGateStatusFromMilestones()` already use for progress-item plot tags — rather than an exact string match; an earlier version used exact matching, which was strict enough that a phone-typed tag or a bare "1" instead of "Plot 1" would silently miss a real plot and fall through to the general list. An apartment block's own name still never matches, since a block has no snag list of its own, only its flats (which, being plots under the hood, match normally). The general-list fallback (title `"Weekly Report Issues"`, `plot_id` null) is get-or-created by a case-insensitive title lookup scoped to `plot_id is null` on that project, so it's reused indefinitely rather than spawning a new list on every report; a plain client-side select-then-insert like this could in principle race under concurrent saves, same as every other get-or-create in this app (e.g. general snag list creation itself) — accepted for the same reason: one site is normally administered by one person at a time. `syncActionRequiredSnags()` re-resolves and re-syncs every Action-Required photo on **every** save, not just the first time — a photo that already has a `snag_item_id` gets its `location`/`description` refreshed from the photo's current category/caption, and is *moved* (its `snag_list_id` updated) if the resolved list has changed since it was raised, rather than being frozen at whatever list it first landed on. This matters in practice: a site manager who types a quick "1" while out on site, saves, then goes back later and tidies the tag to "Plot 1" expects the snag to end up on Plot 1's list, not stuck wherever the first save put it.
- **Audit trail design**: `audit_log` is written to only by `write_audit_log()` — a single generic, `security definer` trigger function attached to 9 tables (`projects`, `project_members`, `quality_gates`, `handover_documents`, `commercial_items`, `snag_items`, `weekly_reports`, `org_settings`, and `actions` since Priority 5 — the last needed no change to this function at all, since its shape already fits the existing generic `project_id` branch), rather than one function per table, using `to_jsonb(NEW/OLD)->>'column'` dynamic lookups so it stays safe across their different shapes (`projects` has no `project_id` — the row itself is the project; `org_settings` has no `project_id` at all, and its legacy `id` column is a `smallint` singleton rather than a uuid, so its audit `record_id` is its `org_id` instead). The actor (`user_id`) always comes from `auth.uid()` — the caller's own authenticated session — never a client-supplied value; `org_id`/`project_id` are derived the same trusted way (looked up from `projects` for child tables), never taken from the row's own client-writable columns. `audit_log` has RLS enabled with a single SELECT policy (`can_read_audit_row()`, mirroring each audited table's own real read rule — several are editor-only to read, not member-level, so a snagging-only member can't see quality-gate or commercial history they couldn't read directly either) and **no INSERT/UPDATE/DELETE policy at all** — Postgres's "RLS enabled, zero policies for an operation" default-denies every client write, so the only way a row can ever be created is via the trigger function itself, making the log append-only and tamper-resistant from any authenticated context. Known, accepted limitations: (1) a superuser/service-role connection bypasses RLS same as anywhere else in this schema — this was never presented as protecting against that; (2) `org_id`/`project_id` are `on delete set null` (never cascade, so deleting a project doesn't destroy its own history) but a row whose reference has been nulled this way becomes unreadable under the SELECT policy except to a superuser — retention/archival of orphaned rows is a deliberate future item, not solved here; (3) only `INSERT`/`UPDATE`/`DELETE` are recorded, never reads or UI interaction; (4) no IP address or user-agent is captured, since this schema has no reliable server-side source for either. Audit history begins from whenever this migration is applied — installing it on an existing database does not fabricate historical records for data or backfills that predate it (see the two "Audit trail" tests in `tests/database/migrations.test.mjs`). Extending coverage to another table is one `create trigger ... execute function public.write_audit_log()` line, no new function needed — `plots`, `blocks`, `drawings`, `specifications`, `internal_milestones`, `monthly_reports`, `hs_audits`/`hs_audit_items`, `snag_lists`, and `organisation_members` were deliberately left out of this first pass as lower-value or noisier to log, not because they're harder to add.
- **Actions Engine design**: `actions` (`sql/schema.sql`, "v29 ADDITIONS") is a first-class, project-scoped table — `org_id`, `project_id`, `title`, `description`, `status`, `priority`, `assigned_to`, `created_by`, `due_date`, `completed_at`, `created_at`, `updated_at` — deliberately built as reusable infrastructure for later modules (inspections, defects, risk, commercial control) rather than tied to any one of them; those integrations are Priority 6+ work, not built here. `org_id` is never client-supplied — a `before insert or update` trigger (`actions_before_write()`) unconditionally re-derives it from `project_id` via a lookup on `projects`, the same principle `audit_log`'s own `org_id` already uses, so a spoofed `org_id` in an insert payload is silently overwritten with the real one rather than trusted. The same trigger unconditionally sets `created_by`/`created_at` on insert (ignoring any client-supplied value) and keeps them immutable on every later update, sets/clears `completed_at` exactly when `status` transitions into/out of `'completed'`, and validates every status change against a small fixed transition table (`valid_action_status_transition()` — `open → in_progress/completed/cancelled`, `in_progress → blocked/completed/cancelled`, `blocked → in_progress/cancelled`, `completed → open` as the one explicit "reopen" path, `cancelled` terminal) — deliberately not a general workflow engine, just enough to prevent nonsensical jumps. Status (`open`/`in_progress`/`blocked`/`completed`/`cancelled`) and priority (`low`/`medium`/`high`/`critical`) are plain `CHECK` constraints, lowercase snake_case to match every other enum-like column in this schema (`quality_gates.status`, `commercial_items.status`, etc.) rather than the uppercase convention sometimes used in planning docs. Access is editor-only (owner/collaborator) via `is_project_editor()`, matching the majority convention already used by `quality_gates`/`commercial_items`/`handover_documents`/`weekly_reports` — snagging-only members see none of this module, unlike their full access to `snag_items`. `assigned_to` references `auth.users` directly (not `project_members`, which is per-project membership rather than identity), but a new parameterised `is_project_editor_user(project_id, user_id)` helper — a twin of the existing `is_project_editor()` that checks an explicit user rather than always `auth.uid()` — is enforced both in the trigger (a friendly error) and in the INSERT/UPDATE RLS policies' `WITH CHECK` (the real boundary): an action can never be assigned to someone who isn't a legitimate editor of that specific project, closing the "assign to someone who shouldn't even be on this project" gap explicitly called out when this was built. Audit integration needed zero changes to `write_audit_log()` or `can_read_audit_row()` (Priority 4) — `actions` has a plain `project_id` column like most audited tables, so it fell straight into each function's existing generic/default-editor-level branch; only one new `create trigger` line was needed. Four indexes, each tied to a real query shape: `(project_id, status)` and `(project_id, due_date)` for a project's action list, `(assigned_to, status)` for a future "my open actions" view, and `org_id` alone (avoiding it ever showing up as an unindexed foreign key, and supporting isolation-style queries). Known limitations / Priority 6+ opportunities: no module currently *creates* an Action automatically from a snag, quality-gate failure, or commercial item — this priority deliberately built the generic engine only, not those integrations; no organisation-level (project-less) Actions, since every real use case so far is project-scoped — worth reconsidering only if a genuine cross-project use case appears; no notifications/reminders for due/overdue actions.
- **Project Control Dashboard design**: no new tables — the dashboard is entirely derived from existing data (`actions` is the primary signal; `hs_audit_items.severity` is the one other real, directly-queryable urgency signal in this schema). `getPortfolioControlSummary()`/`getProjectControlSummary()`/`getAttentionActions()` (`tracker/js/app.js`) issue a small, FIXED number of broad selects — **unfiltered by `project_id`** — and let each table's existing RLS (`is_project_editor()`) do the real scoping, the same pattern `dashboard.html` already used for `snag_items`/`weekly_reports` before Actions existed; a database view/RPC would enforce nothing more, since RLS is the actual boundary either way. This means the query count is `O(1)` regardless of how many projects or actions exist, verified with 25 seeded projects / 500 actions in `tests/security/dashboard_performance.test.mjs`. The one schema addition, `get_my_project_roles()` ("v30 ADDITIONS"), returns the caller's own role on every project they belong to in a single call — added specifically to avoid calling the existing `get_my_role(project_id)` once per project (an N+1 this priority was explicitly built to avoid), needed so a snagging-only member's site can be labelled **"Snagging Only"** honestly rather than showing a fabricated "0 exceptions / On Track" status for control data that role was never entitled to see. Control status is deliberately **not** a numeric score: `computeControlStatus()` returns one of `attention`/`watch`/`on_track` plus a plain-English `reason` string built from the real counts (e.g. "Attention — 2 overdue actions (1 critical), 1 blocked."). Rules: **Attention** — any overdue action, any blocked action, or any unresolved high-severity H&S issue (`hs_audit_items.status = 'non_compliant' and severity = 'high'`). **Watch** (only if not already Attention) — anything due today, due within `DUE_SOON_DAYS` (7, a plain constant), or open high/critical-priority work. **On Track** — no open exception, worded differently depending on whether there's open work with nothing wrong (`"N open actions, no exceptions"`) versus nothing open at all (`"no open actions"`). Quality gates/commercial items/snags are shown as supporting context (`getProjectSupportingSignals()`, project view only) rather than folded into the status calculation — their statuses (e.g. `pending_client_review`) don't carry the same unambiguous "overdue" semantics an Action's `due_date` does, so mixing them in would make the status less explainable, not more. `categoriseAction()` computes independent, non-exclusive flags (overdue/due-today/due-soon/blocked/high-critical) per action, excluding `completed`/`cancelled` entirely from every count. Error handling is deliberate: a failed control-summary query renders as a real error with a Retry button and hides the summary section — it never falls back to showing zeros, which would be indistinguishable from genuinely having nothing outstanding.
- **Inspections design**: three tables (`sql/schema.sql`, "v31 ADDITIONS") — `inspections`, `inspection_findings`, `inspection_finding_photos` — deliberately separate from `hs_audits`/`hs_audit_items`, which is a specific, fixed-checklist MONTHLY H&S compliance mechanism already feeding `monthly_reports`; a genuinely different concept, left completely untouched by this feature. `org_id`/`project_id` follow the same trigger-derived, never-client-trusted pattern `actions` established: `inspections_before_write()`/`inspection_findings_before_write()` (both `security definer`, mirroring `actions_before_write()`) re-derive `org_id` from `project_id` on every write and force `created_by`/`created_at` immutability. The findings trigger additionally enforces two IDOR-closing checks server-side, not just in the UI: a finding's `project_id` must always match its own inspection's `project_id`, and a linked Action (`action_id`) must belong to that same project — both verified adversarially in `tests/security/inspections.test.mjs`. **Actions integration**: `inspection_findings.action_id → actions(id)` — the finding (the origin) references its consequence, not the reverse; adding an `inspection_finding_id` column to `actions` would have coupled the deliberately reusable Actions Engine (Priority 5) to one specific origin module. Nothing creates an Action automatically — `createActionFromFinding()` only ever runs from an explicit "Create Action" click, and moves the finding to `action_required` as a direct, deliberate consequence of that same click (not a background workflow); resolving a finding is always a separate, explicit `resolveFinding()` call — completing the linked Action never does this on its own, verified in `tests/frontend/inspections_workflow.test.mjs`. **Evidence**: `inspection_finding_photos` is a proper relational table (not a jsonb blob), so a finding can carry more than one photo; storage itself needed **no schema change** at all — uploads live at `<project_id>/inspections/...` in the existing `site-photos` bucket, which `site_photos_authorized()` (v27) already authorises via `is_project_editor()` for any area other than `snags`, exactly the tier this module needs. **Access**: editor-only throughout, matching `actions`/`hs_audits`/`quality_gates`/`commercial_items` — not the `snag_items` member-level exception. **Audit**: zero changes needed to `write_audit_log()`/`can_read_audit_row()` — both tables fit their existing generic `project_id`-based branches; `inspection_finding_photos` is deliberately **not** audited (matching this schema's existing convention that not every child table is — `hs_audit_items` itself isn't audited either — the audited unit is the finding's own state, not each evidence upload). **Dashboard integration** (`countFindingSignals()`): a **critical** open finding is always an Attention-level exception on its own; a **high**-severity finding only escalates once it has a linked Action whose own `due_date` says so (findings carry no due date of their own) — overdue → Attention, due soon → Watch — the only two rules the actual data model can support cleanly. Quality gates/commercial items/snags remain unaffected. Known limitation: a high-severity finding with no linked Action produces no dashboard signal at all yet, by design (there's no date to reason about) — raising an Action is what makes it actionable.
- **Defects / Snagging rationalisation design**: this priority was explicitly scoped as inspecting and rationalising the EXISTING `snag_items` system, not building a new one — `snag_items` has existed since before Priority 1 and stays exactly what it always was, a **defect record** (location, description, trade, photo, status). The actual gap, found by inspecting the real app rather than assumed from the schema: `priority` already existed as a column and was already being set and shown by `drawing-view.html`'s pinpoint-snagging flow, but was completely absent from `snag-list-edit.html`'s main everyday form — so every normally-raised snag was silently stuck at the default `'medium'` with no way to see or change it. That's the concrete basis for surfacing `priority` there rather than inventing a parallel `severity` field. The real missing piece was an accountability layer, added additively in "v32 ADDITIONS": `assigned_to` (`uuid references auth.users`, any project role — including snagging-only, since closing out snags is their actual job, unlike Actions' editor-only assignee), `due_date`, `action_id → actions(id)` and `inspection_finding_id → inspection_findings(id)` (both nullable, optional — a snag's origin references its consequence, the same direction Priority 7 established for findings→actions, keeping the reusable Actions Engine uncoupled from this module too), and `verified_at`/`verified_by`. **Resolved vs. verified**: the existing `status` CHECK constraint (`open`/`closed`/`rejected`) is left completely unchanged — a contractor closing a snag is not the same as it being independently confirmed fixed, so verification is two new, separate, nullable columns rather than a new status value with cosmetic meaning. `snag_items_before_write()` (mirroring `actions_before_write()`/`inspections_before_write()`) enforces all of it server-side: `assigned_to` must be a real `is_project_member_user()` (member-level, matching `snag_items`' own long-standing member-level RLS, unlike Actions), a linked `action_id`/`inspection_finding_id` must belong to the *same project* (the same IDOR class Priority 7 closed for findings→actions, closed here for snags→both), and only a project editor (owner/collaborator, not snagging-only) can set or clear `verified_at` — and only once `status = 'closed'`. Reopening a verified snag always clears `verified_at`/`verified_by` as a side effect of the status change itself, with no permission check, since any member can reopen a snag; the trigger captures whether the *client* actually changed `verified_at` before any auto-clearing runs specifically so a plain reopen by a snagging-only member is never blocked by the editor-only check that guards a *deliberate* verification change (see `tests/security/snags.test.mjs` for the exact scenarios this closes). `closed_date` keeps its existing client-settable-with-server-fallback behaviour (`coalesce(new.closed_date, current_date)`) — unchanged from before this priority, since it isn't a security boundary. **Audit**: zero changes needed — `snag_items` has been audited since Priority 4, and `can_read_audit_row()` already bucketed it as member-level; the new columns are picked up automatically by the existing generic `write_audit_log()`. **Dashboard integration**: `countSnagSignals()`/`categoriseSnag()` mirror `categoriseAction()` exactly, since `snag_items` now has its own `due_date` just like `actions` does — overdue is Attention, due-today/due-soon/high-priority-with-no-due-date is Watch (priority alone never reaches Attention, matching how `highCritical` already works for Actions — never a fabricated numeric score). One deliberate exclusion: there is **no** "awaiting verification" dashboard signal — the live production database has ~70 real, pre-existing closed snags that predate verification entirely, and surfacing "closed but unverified" as an exception would misrepresent months of already-accepted historical work as a brand-new backlog. **Evidence**: unlike Inspections' `inspection_finding_photos`, `snag_items` keeps its existing single `photo_url` field rather than gaining a relational multi-photo table — the existing everyday snag workflow (`snag-list-edit.html`) has only ever needed one photo per item, and there's no evidence in the app of a genuine need for more; this can be revisited the same way Inspections' relational table was built, if that changes. Migration is purely additive (nullable columns, new indexes, one new trigger) — see `tests/database/migrations.test.mjs`'s "Defects / Snagging" tests for the exact before/after field-preservation proof against a realistic pre-existing snag. **The three-way distinction this priority had to keep clear**: an Inspection **Finding** is something identified during a structured walk-round; a **Snag/Defect** is a specific physical/technical issue requiring correction (can originate from a Finding, or be raised directly on site via the normal snagging workflow); an **Action** is a task assigned to achieve a required outcome (can originate from a Snag, a Finding, or stand alone, and remains the only task-tracking/assignment system in this app — this priority did not create a second one). Known limitation: a finding that becomes a snag via `createSnagFromFinding()` lands on a shared, auto-created "Inspection Findings" general snag list (the same get-or-create-by-title pattern `weekly-report-form.html` already uses for its own auto-raised snags) rather than being matched to a specific plot, since a finding carries no plot of its own to match against.
- The Site Snag Sheet (`snagging-report.html`) needed no schema change either — it's a read-only query across `snag_items` for the whole project, embedding each item's `snag_lists(title, plot_id, plots(plot_number))` in one `select()` so plot name vs. general-list title can be told apart client-side without a second round trip. The status filter is applied entirely in the browser against one already-fetched full dataset (all statuses, unfiltered) rather than re-querying per filter change, so switching the dropdown is instant and the summary counts (which always reflect every status, not just the currently-shown one) don't need a separate query either. The print CSS rule that keeps a table row or photo card from splitting across a page break was broadened from `.doc-section table tr` to plain `.doc table tr`, since this page's (and `snag-list-view.html`'s) table isn't wrapped in a `.doc-section` — the narrower selector had silently never applied to either.
- **Weekly Reporting design**: `weekly_reports` (existed since v1) needed no change to its rich human-entered content — every progress/weather/labour/risk/commercial/photo field stays exactly what it was. "v33 ADDITIONS" adds only what was genuinely missing: a `status` lifecycle (`draft`/`reviewed`/`approved`/`issued`, `check`-constrained, one step forward at a time via `valid_weekly_report_status_transition()` — mirroring `valid_action_status_transition()`'s exact style — with any-locked-status→`draft` as the single deliberate "Revise" reopening path, the same `completed→open` shape Actions already established), `system_position`/`position_generated_at` (the frozen system-generated snapshot), and `updated_at` (weekly_reports never had one before, unlike `actions`/`inspections`). **Locking**: `weekly_reports_before_write()` refuses any UPDATE where `NEW.status` is `approved`/`issued` and any column other than `status`/`updated_at` differs from `OLD` — computed as a single `to_jsonb(NEW) - array['status','updated_at']` comparison against the equivalent for `OLD`, so a future column added to `weekly_reports` is automatically covered with no trigger change needed, the same dynamic-jsonb approach `write_audit_log()` already uses. This also correctly refuses a single UPDATE that tries to transition into a locked status *and* sneak in a content edit at the same time — verified in `tests/security/weekly_reports.test.mjs` — so Approve/Issue are always pure status actions, never a vehicle for a bundled edit. **The system position** (`getWeeklyReportPosition()`, `tracker/js/app.js`) is deliberately built by REUSING, not reinventing, the exact counting/status functions the Project Control Dashboard (Priority 6-8) already established — `aggregateActionCounts()`, `countHighSeverityHsIssues()`, `countFindingSignals()`, `countSnagSignals()`, `computeControlStatus()` — with the one deliberate difference that every one of them is called with the report's own `week_ending` as the reference date, never `todayISO()`: a report about a past period must always show the same Attention/Watch/On Track position however long after that period it's actually opened, and must be exactly reproducible against fixed dates in a test, never the live clock (`tests/frontend/weekly_report_helpers.test.mjs`). Six broad, `project_id`-scoped queries (actions/snag_items/inspection_findings/inspections/hs_audits/hs_audit_items), each issued exactly once via `Promise.all` — never one per row, never one per section re-fetching the same table — feed both the exceptions computation and a concise **"what changed this period"** activity list built ONLY from genuine existing timestamps (`created_at`/`completed_at`/`raised_date`/`closed_date`/`verified_at`/`resolved_at`/`inspection_date`), deliberately never a raw `audit_log` dump; a currently-blocked or currently-overdue item is a STATE and belongs in exceptions, never in "what changed." **Timezone-safe period matching**: every period-membership check uses `dateOfTimestamp()` (a plain ISO-string slice to the UTC calendar date) rather than any `Date`-object/local-timezone conversion, so two people viewing the same report in different timezones — or a test running in any timezone — always agree on what happened "during" a given reporting period; this is a deliberate, narrow exception to this app's usual local-calendar-date convention (`toLocalISODate()`), justified specifically because period-boundary consistency here matters more than matching the viewer's own clock. **New timestamp**: `inspection_findings.resolved_at` (set/cleared on transition into/out of `resolved`, mirroring `actions.completed_at` exactly) — added because "findings resolved this period" needs a real event timestamp, not `updated_at`, which any unrelated edit (a note, a severity change) would also touch and so would silently over-count. **Snapshot behaviour**: while Draft/Reviewed, `system_position` is only ever refreshed by an explicit "↻ Refresh Position" click (or, once, automatically for a brand-new report or one saved before this feature existed) — opening an existing report never silently re-fetches live data over what was last saved; once Approved/Issued, the trigger above makes this physically impossible to change regardless. **Access**: unchanged — `weekly_reports` was already editor-only (`is_project_editor()`), exactly the same tier `actions`/`inspections`/`hs_audits` already use, so no RLS policy changed; the lifecycle is a trigger-level business rule on top of an already-correct access boundary, not a new one. **Audit**: zero changes needed — `weekly_reports` has been audited since Priority 4 and already sits in `can_read_audit_row()`'s default editor-level bucket; every lifecycle transition (and any rejected locked-content write) is captured automatically by the existing generic trigger. Known limitations: the "what changed" activity list has no equivalent for Commercial Items or Handover Documents yet (out of scope for this priority — `commercial_items`/`handover_documents` were reviewed but deliberately not expanded); a report's period is always exactly its own `week_starting`/`week_ending` — there's no support yet for a report spanning something other than one week.
- **Document Management foundation design (Priority 10)**: a genuinely new concept — `documents` / `document_revisions` (`sql/schema.sql`, "v34 ADDITIONS") — deliberately narrow: Organisation → Project → Document → Revision → File, nothing more. **Why a new table, not an extension of something existing**: every file field already in this schema (`drawings.drawing_url`, `specifications.spec_url`, `handover_documents.file_url`, `snag_items.photo_url`) is a single mutable URL with no history — fine for what each of those actually is, but wrong for a *controlled* document, where "what was Revision 2, and is it still what's on site" has to be answerable with certainty. Rather than bolt revisioning onto four unrelated tables, or build one generic polymorphic `document_links` table (explicitly rejected — see Section 3 of the brief this priority was built from), this is one new, purpose-built pair of tables. **Document vs. Evidence — deliberately kept separate**: a controlled Document (drawing, specification, "other" project record) is something that was *issued* and needs a defensible revision history; operational evidence (snag photos, inspection finding photos, H&S photos, weekly report photos) is something that was *captured* and is fine exactly as a single photo attached to its own record. This priority does not migrate evidence into Documents, and does not build a generic link between them — they stay two different concepts with two different lifecycles. **Revision integrity — the one genuinely load-bearing rule**: `documents.current_revision_id` is never client-settable, under any circumstances. `document_revisions_before_insert()` computes `revision_number` itself (`MAX(revision_number)+1` for that document, exactly `set_snag_item_no()`'s own established pattern, with the same accepted residual concurrent-race risk, backstopped by a real `unique(document_id, revision_number)` constraint — see `tests/security/documents.test.mjs`'s constraint test, which disables the trigger to prove the constraint itself is a genuine backstop and not just decoration). `document_revisions_after_insert()` is the only code path that ever sets `superseded_at` or repoints `current_revision_id` — both writes are RLS-bypassing because the function is `security definer`, the exact same mechanism `write_audit_log()` already relies on to write into the equally client-unwritable `audit_log`. The one new pattern this priority introduced: a transaction-local Postgres GUC flag (`app.allow_current_revision_change`), set to `'on'` for the exact duration of that one internal UPDATE and back to `'off'` immediately after — needed because `documents_before_write()`'s usual "force this column back to OLD" rule (the same idiom `created_by`/`created_at` already use everywhere in this schema) can't otherwise tell an ordinary client UPDATE apart from the system's own legitimate promotion, since both arrive through the identical trigger. `document_revisions` itself has **no UPDATE policy and no DELETE policy for any client** — RLS enabled with zero policies for those operations means Postgres default-denies them entirely (again, the same "enabled, unpolicied = denied" idiom `audit_log` already established), so immutability doesn't depend on application discipline. **Storage — a new private bucket, not the existing public one**: `site-photos` (public, unauthenticated read, path-derived authorization) is correct and completely untouched for everything it already serves. A controlled document is a different trust class, so this priority introduces `controlled-documents` — a genuinely **private** Supabase Storage bucket, with its own path-derived authorization functions (`controlled_documents_path_project()`/`read_authorized()`/`write_authorized()`, the same shape as `site_photos_authorized()`, just simpler since every path here is project-scoped with no org-logo-style exception) mirroring `documents`' own RLS tiers — member-level read, editor-level write, no update/delete policy at all (a fresh random object name is written on every upload; nothing is ever overwritten or deleted). New revisions store the raw object **path** in `file_url`, never a public URL — resolved to a short-lived signed URL (`getDocumentFileUrl()`) or downloaded directly (`downloadDocumentFile()`) at the moment it's actually needed, both through the same authenticated client + real storage RLS every other upload in this app already uses; there is no service-role credential anywhere in this feature. **Migrating Drawings/Specifications — additive, not a cutover**: both tables predate this priority and had zero production rows when it was built, but `drawings.id` is load-bearing for the existing pinpoint-snagging feature (`snag_items.drawing_id`, `quality_gates.drawing_id`, `drawing-view.html`'s whole pin UI) — inspected explicitly before touching anything, per the brief's own instruction. So `drawings`/`specifications` are **not** dropped, emptied, or replaced: the migration is a one-time, idempotent backfill (matched by `project_id` + `document_type` + `title`, so re-running `schema.sql` never duplicates it) that creates a `documents` row + a Revision 1 for each existing legacy row, with `document_revisions.storage_bucket = 'site-photos'` and `file_url` pointing at the **original, unchanged** public object — a migrated legacy file is never re-hosted or re-uploaded into the new private bucket, since plain SQL DDL/DML can't move a real Supabase Storage object; this is a deliberate, honest, documented limitation, not something papered over. The old Drawings & Specification pages keep working completely unchanged for pinning; going forward, new documents (of any type) are created through the new Documents UI instead. **Handover Documents — deliberately NOT touched**: `handover_documents` keeps its own missing/draft_received/approved_final model exactly as it is; this priority was explicitly told not to migrate it, and didn't build any relationship between the two systems — that's left for a future priority to consider once there's a real reason to. **Audit**: zero changes needed to `write_audit_log()` — both new tables have a plain `id` + `project_id`, so they fall straight into its existing generic branch; `can_read_audit_row()` gained `documents`/`document_revisions` in its member-level bucket (alongside `projects`/`snag_items`) specifically so a snagging-only member, who can read the documents themselves, isn't shown a false "no audit history" for something they're otherwise allowed to see. **Delete behaviour**: deliberately conservative, per the brief — there is no delete anywhere in this feature, at the database, RLS, or UI level. Retiring a document is `status = 'archived'`, which preserves every revision, every file, and the full audit trail; this closes off an entire class of storage-orphan risk this table would otherwise have, at the cost of no built-in cleanup for anything genuinely unwanted — a known, accepted limitation, not solved here.
- **Bulk Export design (Priority 10)**: entirely client-side — this app has no backend/API to maintain (`tracker/js/supabase-client.js` + the anon key + RLS is the whole access model), and the brief explicitly ruled out direct Microsoft Graph/SharePoint integration for this priority in favour of "a high-quality bulk export that works cleanly with Microsoft 365/SharePoint." `exportDocumentsZip()`/`planDocumentExport()`/`sanitizeExportFilename()`/`exportFilenameFor()`/`dedupeExportFilenames()`/`buildExportManifestCsv()` (`tracker/js/app.js`) build a ZIP with [JSZip](https://stuk.github.io/jszip/), loaded on demand from esm.sh — the exact same on-demand-CDN-import approach already established for SheetJS in `plot-handovers.html`'s Export Trackers, so this needed no new dependency-loading pattern. **Security**: every file the export reads goes through `downloadDocumentFile()`, the same authenticated client + real storage RLS as everything else — an export can never contain a document the signed-in user's own RLS-scoped queries didn't already return, so the export surface adds no new access-control boundary of its own; the adversarial cases are already covered by `tests/security/documents*.test.mjs`, not re-tested at the export layer. There is no service-role credential involved anywhere. **Planning is deliberately pure**: `planDocumentExport()` computes every (folder path, filename) entry with zero network/file I/O, specifically so the folder-structure/naming/de-duplication logic is unit-testable without JSZip or a mock filesystem (`tests/frontend/documents_export_helpers.test.mjs`) — `exportDocumentsZip()` itself is a thin wrapper that plans first, then fetches. **Default is current-revision-only** — exporting every historical revision by default was explicitly ruled out by the brief; **Include revision history** is an opt-in toggle that reorganises the same document's entries into `<Type Folder>/<Document>/Current/` and `.../Revision History/` subfolders, still going through the same planning function. **Filenames**: `[Doc Number] - [Title] - Rev [N].ext` (or without the doc number, if there isn't one) — cleaned of every character Windows/SharePoint disallow, trimmed of a trailing dot/space (a Windows-specific rule), capped at 150 characters; the true original filename is never destroyed by this — it stays visible in the app (`document_revisions.file_name`) and in the manifest. Two documents that would otherwise produce the exact same export filename in the same folder are de-duplicated deterministically (`Name (2).ext`, `Name (3).ext`, ...) — the ZIP must never silently let one file overwrite another. **Export limit**: a client-side ZIP has to hold every exported file in memory at once, since there's no server to stream through — capped at 150MB (`EXPORT_MAX_TOTAL_BYTES`), checked against the sum of `file_size` across the planned export *before* any file is fetched, and it fails loudly with a clear message (narrow your selection or filters) rather than silently truncating; this is an explicit, documented limit, not a silent constraint. **Manifest**: `Export Manifest.csv` at the root of the exported project folder — project/title/type/number/revision/status/original filename/export filename/exported date, properly CSV-escaped — deliberately simple (no attempt at a richer format), matching the brief's own "keep this simple" instruction.
- **Programme Control design (Priority 11, Phase 2)**: `programmes`/`programme_activities` (`sql/schema.sql`, "v35 ADDITIONS") are a genuinely new pair of tables built from a Phase 1 inspection that found **no** existing programme/schedule data model anywhere in this app — every "progress" signal that existed before this (`plots.progress_pct`, `internal_milestones.percent`, `weekly_reports.programme_status`) was a manually-set or milestone-tag-derived percentage with no planned date behind it at all. The agreed architecture is **hybrid**: an external tool (MS Project/Asta/Primavera/Excel) remains the actual place a programme gets planned — this app is explicitly NOT trying to become a scheduling engine — and imports/records planned dates, then owns forecast, actual, status and progress on top. **What this phase deliberately does NOT build** (all explicit future phases, not oversights): a Gantt chart, a dependency/critical-path engine, programme versioning/re-baselining, a Project Control Dashboard integration, a Weekly Report integration, or a working XLSX importer UI — only the import *architecture* (the data contract, validation rules, and stable-identity strategy) was established this phase, not the reader/upload/preview UI itself.
- **Why one `programmes` row per project rather than folding straight into `projects`**: a programme has its own lifecycle (Draft → Active → Archived) independent of the project's own `status`, and — even though this phase deliberately does not build re-baselining/versioning — modelling it as its own row now means a future "multiple programme versions" phase is an additive change (more `programmes` rows), not a schema redesign. Enforced with a **partial unique index** (`programmes_one_active_per_project on programmes(project_id) where status = 'active'`) rather than a trigger — always correct under concurrent writes, the same guarantee `unique(document_id, revision_number)` already gives `document_revisions` in Priority 10, and needs no extra code. Draft/archived programmes are deliberately unconstrained this way — a project may accumulate several archived programmes over time (a genuine historical record), and nothing stops more than one draft existing while it's being set up. Programme `status` is **not** force-reset to `'draft'` on insert — a client may create a programme already `'active'` directly, mirroring `actions_before_write()`'s own established looseness (status is only ever checked on UPDATE via a transition table there, never reset on INSERT) rather than `weekly_reports`' stricter, deliberately-enforced "always starts as draft" lifecycle — a considered choice, not an inconsistency, since this phase never asked for a transition-restriction engine on programmes either.
- **Deviations from the Phase 1 field proposal** (per the brief's own instruction to challenge every field, not implement it by default): `activity_type` was **dropped** — it would have been either a second, competing way to say "is this a milestone" alongside `is_milestone`, or an unconstrained free label duplicating what `title` already says; nothing needed it, so it wasn't shipped as decoration. `sort_order` was **dropped** — only meaningful once a drag-reorder or fixed-sequence UI exists (unlike `quality_gates`/`internal_milestones`' own `sort_order`, which orders a genuinely fixed, auto-seeded list); this phase's list page sorts by real dates instead. The proposed free-text `responsible_party` was **replaced** with `assigned_to uuid references auth.users` — a real project member, validated the same way `actions.assigned_to`/`snag_items.assigned_to` already are, rather than inventing a parallel identity model. One field was **added** that Phase 1 never listed: `external_id text` — required by this phase's own brief once "is this the same activity I imported last week?" had to be answered architecturally; see the import section below.
- **`assigned_to` is validated at MEMBER level, not editor level** — a deliberate divergence from `actions.assigned_to` (which requires a project editor). The person actually responsible for getting a piece of site work done is very often a snagging-only main-contractor contact who has no reason to be able to edit the programme itself — the same distinction `snag_items.assigned_to` already draws. A snagging-only member can legitimately be assigned an activity even though they can't see or edit Programme Control at all (it's editor-only throughout — see below) — the assignment is recorded, they just never see it through this app yet.
- **Planned / Forecast / Actual, never collapsed into one**: `planned_start`/`planned_finish` are the imported baseline plan; `forecast_start`/`forecast_finish` default to the planned dates on INSERT (via `programme_activities_before_write()`) if not explicitly supplied, so a freshly-created activity always has a sane forecast rather than an ambiguous null — and are never silently overwritten again after that. `actual_start`/`actual_finish` are confirmed reality. All three pairs have their own `finish >= start` CHECK constraint (nulls allowed either side, so a milestone can carry just one date). No `baseline_finish` distinct from `planned_finish`, and no historical forecast snapshots — both explicitly out of scope for this phase, per the brief.
- **Status/percent/actual_finish coupling, enforced server-side, not in JS**: marking an activity `status = 'complete'` forces `percent_complete` to 100 (never trusts a lower client-supplied value) and stamps `actual_finish` to today **once**, only on the transition into complete, and only if the client hadn't already supplied a real date — it is never force-overwritten on every subsequent save the way `actions.completed_at` is, since `actual_finish` is a real-world construction date a user may need to correct afterwards while status stays `complete`. **Reopening a complete activity deliberately leaves `actual_finish` untouched** — the one considered divergence from `actions.completed_at` (which always clears itself on reopen): a real date the work finished doesn't become untrue just because the record is reopened for correction. `status = 'not_started'` symmetrically forces `percent_complete` to 0. A client sending an out-of-range `percent_complete` (e.g. 150) alongside the default `not_started` status is *silently coerced* to 0 by this same rule rather than rejected by the `CHECK (percent_complete between 0 and 100)` constraint — that CHECK is the real backstop for every OTHER status (`in_progress`, `cancelled`), where nothing forces the value; see `tests/security/programme.test.mjs` for both cases exercised explicitly. Deliberately **no transition-restriction trigger** on `programme_activities.status` (unlike `actions_before_write()`'s `valid_action_status_transition()`) — programme activities are frequently bulk-imported or corrected with an arbitrary starting status (a mostly-finished programme imported retroactively, or a reopened "complete" activity after a defect is found), and restricting that would actively hinder the legitimate import/correction use cases this table exists to support.
- **The two IDOR classes this priority had to close, mirroring Priority 7/8/10's own established pattern**: `programme_activities.plot_id`, if supplied, must belong to the SAME project as the activity's own (derived) project — validated server-side in `programme_activities_before_write()`, never trusted from the client; and `org_id`/`project_id` themselves are always derived from the parent `programme_id`, never accepted from the client, closing the "attach an activity to a programme in another project" class the same way document_revisions closed it for documents in Priority 10. Both verified adversarially (a spoofed `project_id` on an insert, a plot from a different project) in `tests/security/programme.test.mjs`.
- **Security tier: editor-only throughout, unlike Documents' member-level read** — the brief was explicit: "Do not widen access to snagging-only users yet." Both `programmes` and `programme_activities` use `is_project_editor(project_id)` for every operation, matching `actions`/`inspections`/`hs_audits`' own tier, not `documents`/`snag_items`' member-level read exception. `can_read_audit_row()` needed **zero changes** for this — its existing default (editor-level) branch already matches these tables' own SELECT RLS, unlike Documents in Priority 10, which needed adding to its member-level bucket. `programmes` has **no DELETE policy at all** (retired via `status = 'archived'`, matching the entire purpose of that column) — but `programme_activities` **does** allow an editor to DELETE (unlike `documents`/`document_revisions`), since there's no revision-history concept to protect here and removing a wrongly-imported or duplicate row is normal, expected editing, per the brief's own explicit allowance of "delete/archive" in the UI.
- **Audit**: zero changes needed to `write_audit_log()` — both new tables have a plain `id` + `project_id`, so they fall straight into its existing generic branch, the same as every prior priority's own audited tables.
- **Import architecture (established this phase, not yet a working importer)**: the brief's central question — "is this the same activity I imported last week?" — is answered by `external_id text`, unique per `(programme_id, external_id)` via a **partial** unique index (`where external_id is not null`), scoped to one programme so the same `external_id` can validly recur across different programmes. When the source has no stable ID of its own, the documented fallback is `(plot, title)` matching — never title alone, since two different plots very plausibly share an identical activity title (e.g. "1st Fix – Electrical") and a title-only match would silently merge two different activities. `matchImportRowToActivity()`/`validateImportRow()`/`parseImportDate()`/`planProgrammeImport()` (`tracker/js/app.js`) implement this contract as pure, synchronous, fully-tested functions with **zero** network access or XLSX parsing — deliberately separated from any real I/O the same way `planDocumentExport()` was in Priority 10, so the planning logic (row validation, create-vs-update matching, plot resolution) is provably correct before a single byte of a real workbook is ever read. `PROGRAMME_IMPORT_OWNED_FIELDS` (title/planned dates/is_milestone/external_id/plot_id) and `PROGRAMME_APP_OWNED_FIELDS` (forecast/actual/status/percent_complete/assigned_to) are kept as two explicitly non-overlapping lists (asserted disjoint in `tests/frontend/programme_import_contract.test.mjs`) — `planProgrammeImport()`'s update payloads are constructed ONLY from the import-owned list, so a future re-import can never silently clobber this app's own forecast/actual/status work, the brief's own explicit critical requirement. **Not built this phase**: `XLSX.read()` itself, column-mapping UI, a preview screen, or the actual insert/update calls a real import would issue — those are Phase 3 work, once there's a genuine need proven by this foundation actually being used.
- **Storing the imported file itself**: not implemented this phase (no importer exists yet to produce one). The recommended future approach, once it is needed: extend `documents.document_type`'s existing CHECK constraint with a `'programme'` value — the constraint was explicitly designed in Priority 10 to support exactly this ("additional document types can be added later without schema redesign") — and store the raw uploaded workbook through the existing `documents`/`document_revisions` system rather than inventing a second file-storage path. No migration for this was applied now, since nothing in this phase needs it yet.
- **UI**: `programme.html` is deliberately a practical table, not a Gantt — create/edit/delete an activity, filter by status, sort by finish date/title/status, and switch between multiple programmes for a project via a dropdown when more than one exists (draft-in-progress alongside an active one, say). No timeline visualisation, no drag/drop, no dependency lines. Like `hs-audits.html`, the page has no explicit role-check of its own — access is entirely enforced by RLS and by the page never being linked from a snagging-only member's project view (`project.html`'s `applySnaggingOnlyView()` hides the Programme tile the same way it already hides Actions/Inspections/H&S Audits).
- **Performance**: `(project_id, status)` and `(project_id, forecast_finish)` on `programme_activities` are the two indexes tied to a real query shape this phase actually issues (a project's activity list, and "what's coming up/overdue" sorting) — verified with 50/500/5,000 seeded activities in `tests/security/programme_performance.test.mjs`, unaffected by 15 other projects' own activities in the same organisation. A `planned_start` index (listed as a candidate in the original brief) and a `plot_id` index were both deliberately omitted — nothing this phase sorts/filters by start date alone or looks up activities by plot; trivial to add once a real query needs either. Bare `org_id` indexes on both tables exist purely to avoid Supabase's "unindexed foreign key" advisor warning, matching every other org-scoped child table's own convention in this schema, not because of real query volume (a project typically has 0-2 `programmes` rows).
