# Site Tracker

A small internal app for logging **weekly reports** and **snagging sheets** per site, and sending them to your main contractor. Lives at `/tracker/` on this site. Plain HTML/JS, no build step — same as the rest of this repo — backed by [Supabase](https://supabase.com) for login, the database, and photo storage.

## What it does

- **Sites** — one entry per project (address, contract ref, main contractor name/email, status).
- **Company logo** — set once in **Settings**, it appears on every printed weekly report and snag list.
- **Weekly reports** — a client-side Clerk of Works compliance record: programme status, a day-by-day weather tracker (see below), a **Verified Quality & Works Audit** table (each progress line has a plot/unit, a build-stage trade/work package, a contractor %, and a Clerk of Works quality verification note, e.g. "Pre-plaster check signed off"), a **Labour & Site Resource Tracker** (trade, headcount, activity/location, resource adequacy), H&S notes, a **Risk & Delays Tracker** (description, action required, owner, target date, an impact traffic light), a **Statutory & Testing Milestones** log (air permeability/sound/drainage pressure tests, Building Control/NHBC/Premier inspections and sign-offs), commercial items raised that week (see below), a "plan for next week" list, a general "other comments" field, and a tagged **photo gallery** — every photo carries a plot/area, an inspection category/element, a compliance status badge (Approved / Compliant, Action Required, Info Only), and a caption. A new report defaults "Week starting" to this week's Monday and "Week ending" to that same week's Friday, matching the Mon-Fri working week the weather tracker already uses — both are ordinary date fields you can still adjust by hand. Every report has a clean printable view, with photo cards and table rows kept from splitting across a page break in the PDF.
- **Weather tracker** — a 5-day grid (Monday–Friday of the report's week, built automatically from "Week starting") for logging condition and lost time per day, plus notes, with a live-computed total. The condition dropdown is Dry, Light Rain, Heavy Rain, Snow / Ice — leaving a day blank still means nothing to report; Dry is there for when you want a day explicitly on record as checked and clear, not because every day needs a condition set. The old single "weather" line is kept as an optional "Weather Notes" field for anything that doesn't belong to one specific day. Shown on the printed weekly report as a full day-by-day table, and rolled up into the monthly report as a month total plus a breakdown of just the days that lost time.
- **Weather auto-fill** — if a site has a postcode set (Site Details → Edit), the weather tracker looks up real weather for that location and pre-fills each day's condition automatically (using [Open-Meteo](https://open-meteo.com), free and keyless) — only days with rain or snow get filled in, so you just add lost hours and notes where they matter. It never overwrites a day you've already set, and quietly does nothing if the postcode isn't geocodable or the lookup fails — auto-fill is a convenience, never a requirement. The postcode is geocoded once (via [postcodes.io](https://postcodes.io), also free and keyless) and the coordinates cached on the site, so it's only looked up again if you change the postcode.
- **Build milestone tagging** — each progress/next-week line can be tagged with a build stage from a fixed dropdown (Site Set-Up, Groundworks, Foundations, Drainage, Slab Pour, Timber Frame, Superstructure, Scaffold Erect, Roofing, Windows & Doors, Scaffold Drop, Render, Cladding, 1st Fix split by trade — Carpentry, Electrical, Plumbing & Heating, Gas — Plastering, 2nd Fix split by trade — Carpentry, Electrical, Plumbing & Heating — Kitchen Fit, Bathroom Fit, Painting & Decorating, Flooring, Solar Panels, External Works, Testing & Commissioning, Snagging, Handover/PC) — or pick "Other" to type your own. The item text itself is optional once a milestone is set, so a line can just be "1st Fix – Electrical" with a % complete. The milestone list lives in `BUILD_MILESTONES` in `tracker/js/app.js` if you want to add/reorder stages.
- **Plot tagging on weekly reports** — the plot field on each progress/next-week line is a multi-select of the site's actual plots and apartment blocks, not freetext, so a line can be tagged to one or several at once (e.g. logging "1st Fix – Electrical" against Plot 3 and Plot 4 in one line, or "Frame Erect" against a whole block in another). Editing an older item that was tagged before this existed keeps its original freetext plot name(s) selectable too, so nothing gets silently dropped. The picker also always offers **External / Engineering Works** as a permanent, site-wide option alongside the plots and blocks — tag milestone items to it the same way, then use **Suggest from Milestones** next to the External / Engineering Works % field on Site Details to pull a starting-point % from whatever's been logged against it (same "fills the box, you hit Save" behaviour as a plot's or block's own Suggest button — never auto-overwrites). Milestones tagged to a block feed its own Suggest from Milestones on the block's page, same as a plot's.
- **Weekly reports auto-advance Plot Handovers** — for standalone houses (not flats or apartment blocks yet), once every milestone that makes up one of a plot's 4 quality gates has been logged at 100% against that plot across its weekly reports (deduped the same way as "Suggest from Milestones" — highest % ever reached, regardless of which report it was logged in), that gate's status automatically moves to **Under Review** — e.g. all four 1st Fix trades plus Plastering complete moves Pre-Plaster/First Fix to Under Review. It only ever moves a gate forward from Not Started/In Progress, and only ever as far as Under Review — a gate that's already Under Review, Approved, or marked N/A is never touched, and nothing here ever sets Approved itself, which always stays a person's decision on the plot's own page. The milestone groupings live in `GATE_MILESTONES` in `tracker/js/app.js`.
- **Week-to-week progress carry-forward** — starting a new report pre-fills "Progress this week" from the *previous* report's "Plan for next week", each line getting a % complete field (you can still add fresh items too). Anything left under 100% automatically rolls into that week's own "Plan for next week" so it shows up again next time — no manual re-typing. Hit 100% and it drops off for good.
- **Monthly reports** — on the Monthly Reports page, pick a month and hit "Generate Report" to roll every weekly report from that calendar month into one saved, printable summary: total weather lost time for the month plus a day-by-day breakdown, progress by milestone (deduped by item, so a milestone tracked across several weeks shows up once with its highest % reached — and still shows as completed even if it dropped off the weekly list after hitting 100%), outstanding items going into next month, H&S notes and issues/risks per week, that month's H&S Audit(s) (see below), commercial items raised that month with totals by type, snags raised/closed that month, a plot handovers snapshot, and a combined photo gallery. Generated reports are saved snapshots — editing a weekly report afterwards won't change a month you've already generated; delete and regenerate if you need to pick up changes.
- **Snagging** — organised **per plot**, using the same `plots` you add on Plot Handovers. Each plot gets exactly one snag list, created automatically the moment the plot is added; click into a plot to add as many items to it as you like (location, description, trade, photo — each editable and deletable), then export that plot's list as a PDF. Each item's status is **Open**, **Closed**, or **Rejected** (for one the contractor disputes), plus an independent **⚠️ Flag Delay** for anything stuck waiting on something, with a reason — a flagged snag stays Open until it's actually closed or the flag's cleared, it's not a status of its own. Priority and "raised by" have been dropped from the item form to keep it quick to fill in on site. See "Snagging-only access" below for inviting someone who should only be able to work with snags.
- **General / Site Visit snag lists** — for a walk-round that isn't about one plot (touring several plots in one go, or logging a site-wide/external issue), hit **+ General List** on the Snagging page instead of clicking into a plot. Name it whatever you like (defaults to "Site Walk - [today's date]") and it gets its own card in a separate "General / Site Visit Lists" section above the plots table. Each item you add to a general list carries its **own Plot** dropdown (any plot on the site, or "External / Site-wide" for something that isn't tied to one) — everything else about the item (location, description, trade, photo, status, delay flag) works exactly the same as a plot-specific snag. You can create as many general lists as you like. These stay deliberately separate from the per-plot Open/Closed/Rejected counts on the Snagging page and from the monthly report's plot handovers snapshot — a general list's items aren't rolled into either. A general list you no longer need can be removed entirely with the **Delete List** button on its own page (deletes every item in it too). Plot-specific snag lists don't get this button — they're tied one-to-one with their plot, so deleting one is done from the Plot Handovers page by deleting the plot itself.
- **Weekly report photos auto-raise snags** — tag a weekly report photo's compliance status as **Action Required** and it's automatically raised as a snag when you save the report — no separate trip to Snagging needed. The photo's Plot/Area tag is matched against the site's real plots the same digit-based way plot tags are matched everywhere else in this app (so "Plot 1" and "1" both resolve to the same plot); if it matches, the snag lands on that plot's own snag list (location = the photo's Inspection Category/Element, description = its caption, same photo attached). If it doesn't match a real plot — a typed-in area like "S278 Entrance", an apartment block's own name, or left blank — it lands on a shared general list called "Weekly Report Issues" instead (created once per site, reused every time), with the plot/area tag folded into the snag's location so the context isn't lost. A photo already raised shows a **✓ Snag Raised** badge (linking to the snag on the printed report); editing that same photo's tag/category/caption and saving again keeps the snag in sync — including moving it to the right plot's list if you go back and correct the tag — rather than freezing it wherever it first landed.
- **Sending to the contractor** — every report/snag list has a "Print / Save as PDF" button (uses your browser's print-to-PDF) and an "Email to Contractor" button that opens a pre-filled email to the contractor's saved address — attach the PDF you just saved. A weekly report's suggested filename is "Weekly Report - [Site Name] - [Week Ending as d.m.yy]" (e.g. "Weekly Report - Red Dragon - 21.8.26") — browsers use the page title as the default PDF filename, so this is set from the report's data before you print.
- **RAG status & plot-based progress** — set an overall Red/Amber/Green status and a planned/baseline progress % by hand (Site Details → Edit). Actual Progress is a *weighted* average: every standalone plot/flat's own progress % counts once (set directly on that plot's page, under Plot Handovers), every apartment block's own progress % (set on the block's page — see below) counts once **per flat in that block** — since a block's shared structure/civils underpin every flat sitting on top of it, a fully-built frame under 30 still-empty flats is genuine, substantial site progress, not something that should barely move the needle — and a site-wide **External / Engineering Works %** (Site Details → Edit, for civils/drainage/landscaping that isn't any one plot or block) counts once. A block with no flats yet counts as a single unit, same as a plot, so it isn't invisible in the average before any flats are added. Every one of those numbers is set by hand, so it's always correctable — nothing recalculates itself and silently overwrites a number you've typed. On a plot's or block's page, **Suggest from Milestones** will fill in a starting-point % computed from the build milestones logged against that plot/block (matched by name) across all its weekly reports (deduped, so a milestone logged in several weeks only counts once, at its highest % reached) — it only fills the box, you still have to hit Save. Shown as a badge and dual progress bar on the dashboard and site page, with a plain-English slippage line ("-5% Behind Programme" / "On Programme" / "+X% Ahead").
- **Plot Handovers** — quality gates, statutory handover documents, and progress % are tracked **per plot**, not once for the whole site, since each house/unit goes through its own sign-off. Add a standalone house with **+ Plot**, or set a **Total Plots** target on Site Details and hit **Generate Missing Plots** there to bulk-create the rest in one go (named "Plot 1", "Plot 2", … skipping any that already exist by name, so re-running it later after adding more just fills the gap). Every standalone plot automatically gets its own 4 quality gates (Substructure & Drainage, Frame & Wind/Watertight, Pre-Plaster/First Fix, Pre-Handover/PC — each with a status, an N/A option for gates that don't apply to that plot, and a checklist that timestamps sign-off when ticked), 5 statutory documents (Building Control, air permeability/acoustic certs, electrical & gas certs, warranty cover note, O&M manuals — each with a status and a real file upload, stored in Supabase, not a mock), and its own snag list. Gates marked N/A are left out of "X / Y approved" counts entirely — on both sides of the fraction — so marking one N/A can only help a plot's ratio, never hold it back; a plot with everything else approved shows as fully complete. Total Plots is just a target count for the bulk-create action above — it has no effect on Actual Progress, which is always just the average of however many plots/blocks actually exist.
- **Apartment blocks** — for sites built as full apartment blocks rather than individual houses, add a block with **+ Block** instead of a plot. A block gets its own page with a **Block Progress** %, its own 4 shared quality gates (Substructure & Drainage, Frame & Superstructure, Roof & Building Envelope, Communal Areas/M&E/Fire Strategy) and 5 shared handover documents (Building Control, warranty cover note, fire strategy report, communal M&E pack, buildings insurance) — tracked **once for the whole block**, not duplicated per flat, since foundations/frame/roof/communal areas are single pieces of work regardless of how many flats sit on top of them. When you create a block you can optionally type its flats' actual plot numbers right away — a range like `23-30`, a comma list like `23,25,28`, or a mix of both — to bulk-create flats named exactly that (a block's flats are often numbered to continue the site's own numbering rather than restart at 1, so nothing forces a "Flat N" name onto them). Leave it blank to add flats one at a time with **+ Flat** on the block's page afterwards, which takes the same range/list input (or just a single number) any time — adding exactly one jumps straight to its page, adding several returns you to the block. Re-running either with numbers that already exist on that block just fills in whichever are missing. Each flat is a normal plot under the hood (so it shows up in Snagging and gets its own progress % and Suggest from Milestones the same as a house), but with a smaller, fit-out-focused set of gates (1st Fix, 2nd Fix, Kitchen & Bathroom Fit, Decoration/Flooring/Pre-Handover Snagging) and documents (air permeability/acoustic cert, electrical & gas certs, EPC, unit warranty cover note, O&M manuals) — the structural sign-offs live on the block instead. Deleting a block deletes all its flats (and their gates/documents/snags) along with it — you're warned before this happens. Plot Handovers lists standalone plots and blocks separately; a flat only ever appears under its block, not in the standalone plots list.
- **Commercials** — an early warning / proposed variation / instruction log per site, with cost and time impact, a status (pending/approved/rejected), and running totals for approved variations and pending exposure. You can log items directly on the Commercials page, or add them under "Commercial items this week" on a weekly report — those are pushed into the ledger automatically when the report is saved (a 📋 icon on the ledger links back to the report it came from). Editing an already-pushed item's title/type/cost/time on the report updates that same ledger entry; removing it from the report's own list never deletes the ledger entry — the ledger is the durable record once an item exists there.
- **H&S Audits** — a separate section per site, expected once a month. Hit **+ New Internal Audit** on the H&S Audits page to walk a fixed, condensed checklist (Statutory Documentation, General Requirements, Site Based Hazards, Environmental — the list lives in `HS_CHECKLIST` in `tracker/js/app.js`) — each item defaults to **Compliant** and you flip any exceptions to **Non-Compliant**, **N/A**, or **Good Practice**, with a note and an optional photo per item. Marking something **Non-Compliant** reveals a traffic-light **Severity** (Low/Medium/High, shown Green/Amber/Red) for how serious that particular issue is. A score % (excluding N/A items from both sides of the fraction, same rule as the quality-gates ratio) and a flagged count are shown on the audit and in the list. **+ Upload External Audit** logs a third-party audit (e.g. a SHE inspection PDF) instead — just a file and who conducted it, no checklist. Either type is logged against a calendar month (independent of the date you actually did it, so a late upload can still count for the month it covers) — if the current month doesn't have one yet, a **⚠️ No H&S audit logged this month** flag shows on the H&S Audits tile on the site page, and the monthly report carries the same flag for any month it rolls up with none. The monthly report also lists whichever audit(s) *did* happen that month, with their score/flagged count or file link.
- **Drawings & Layouts / Pinpoint Snagging** — upload an overall site layout (reference only) and per-plot floor plans. Click anywhere on a floor plan to drop a pin and raise a snag at that exact spot; existing pins are clickable and show the snag's details, status and photo. Pins are stored as a percentage of the image's width/height, so they land in the same spot on any screen size.
- **Multiple accounts & collaboration** — each site has an **owner** (whoever created it) and any number of **collaborators**, who get full edit rights on that site's reports, plots, snags, gates, documents, commercials and drawings — same as the owner. Only the owner can delete the whole site or manage who has access. To bring someone else onto a site, open it and go to the **Collaborators** card → **Get Invite Link**, then send that link however you like (WhatsApp, email, Slack — there's no auto-send, same as everywhere else in this app). Whoever opens it while signed in (or signs up first, then is sent straight back to it) joins instantly — no approval step. **Regenerate** swaps in a fresh link, invalidating the old one; **Revoke** turns it off entirely. Anyone (owner or collaborator) can leave a site from that same card; only the owner can remove someone else. Your dashboard only ever shows sites you're the owner of or a collaborator on — creating a new site makes you its owner automatically. The company logo (Settings) stays shared across everyone regardless of which sites they're on, since it's one company's branding, not a per-site setting.
- **Snagging-only access** — a third membership tier, for whoever actually closes out snags on site (e.g. the main contractor's site manager) but shouldn't see anything else. They can fully manage snag items — add/edit, upload photos, and set the status to **Open**, **Closed**, or **Rejected** (for a snag the contractor disputes is actually a defect), plus raise a **⚠️ Flag Delay** on any snag that's stuck waiting on something (with a reason), separately from its status — a flagged snag stays Open (still outstanding) until it's actually closed or the flag is cleared. They can't see weekly reports, quality gates, statutory documents, the commercial ledger, other drawings, monthly reports, apartment blocks, site details, or the collaborators list — enforced at the database level, not just hidden in the UI. The Collaborators card has a **second, separate invite link** just for this ("Get Snagging Invite Link") — send the right one to the right person, no extra step needed to downgrade anyone afterwards. Opening a site they only have snagging access to shows a cut-down page with nothing but a Snagging tile.

There's no login for the contractor — they only ever receive the PDF/email you send them.

## One-time setup

1. **Create a free Supabase project** at [supabase.com](https://supabase.com) (the free tier is more than enough for this).
2. In the Supabase dashboard, go to **SQL Editor → New query**, paste in the contents of [`sql/schema.sql`](../sql/schema.sql), and run it. This creates the tables, security policies, and the `site-photos` storage bucket.
3. Go to **Project Settings → API** and copy the **Project URL** and the **`anon` public key**.
4. Open `tracker/js/config.js` and paste them in:
   ```js
   export const SUPABASE_URL = "https://xxxx.supabase.co";
   export const SUPABASE_ANON_KEY = "eyJ...";
   ```
   The anon key is safe to ship in client-side code — the SQL script's Row Level Security policies are what actually control access (any signed-in user can read/write; nobody else can).
5. Deploy as normal (this repo's Cloudflare Pages integration picks up static files automatically). Visit `/tracker/`.
6. On first visit, click **Create one** on the sign-in page to make your first account (yourself). Anyone else on your team can do the same — Supabase's default settings will email a confirmation link.

### Updating an existing project (schema changes)

`sql/schema.sql` is written to be safe to re-run in full any time it changes — every statement is `if not exists` / `create or replace` / `drop policy if exists`. If you already have a Supabase project set up, just paste the **whole current file** into SQL Editor and run it again to pick up new tables/columns; nothing existing gets dropped or overwritten destructively.

### Turning off "confirm your email" (optional)

By default Supabase requires clicking a confirmation link before a new account can sign in. For an internal team tool you may prefer to skip this: in the Supabase dashboard go to **Authentication → Providers → Email** and turn off "Confirm email". You can also just leave it on — it only adds one click the first time.

## Adding a team member

Have them sign up from the login page themselves (or Supabase → **Authentication → Users → Add user**). A new account starts with **no sites** — send them an invite link from the specific site(s) they need (Site page → Collaborators → Get Invite Link) to bring them onto it.

## Notes for future changes

- All data access goes through the Supabase JS client (`tracker/js/supabase-client.js`) using the anon key + Row Level Security — there's no custom backend/API to maintain.
- Photos are stored in the public `site-photos` bucket so they load in printed/PDF reports without needing auth headers. If snag/report photos ever need to be private, switch the bucket to private and swap `getPublicUrl` for `createSignedUrl` in `tracker/js/app.js`.
- Weekly report, snag, and handover photos are resized (max 1920px on the longest side) and re-encoded as JPEG at ~78% quality in the browser before upload (`compressImage`/`uploadImage` in `tracker/js/app.js`), to keep Supabase's free 1GB storage tier from filling up. A typical phone photo drops from 5–8MB to under 1.5MB. The company logo (Settings) is deliberately left uncompressed — it's a single file, and re-encoding could strip transparency from a PNG logo.
- Drawings (site layouts, plot floor plans) go through the same idea at higher settings for legibility — resized to max 2560px and re-encoded as WebP at ~75% quality (`compressDrawing`/`uploadDrawing` in `tracker/js/app.js`). Verified against a realistic 6.6MB/5000×3500 test scan: came out at 2560×1792 / 390KB. **PDF drawings are the one exception** — browsers have no built-in way to rasterise a PDF via the Canvas API, so PDF uploads are stored as-is, unconverted and uncompressed, and are view/download-only (no pinning). If you regularly upload PDF drawings and storage becomes a concern, export them as PNG/JPG before uploading, or ask for a PDF→image conversion step to be added (it would need a library like `pdf.js`, which is a much heavier addition).
- Quality gates already have `drawing_id`/`x_coordinate`/`y_coordinate` columns (for pinning a gate to a location on a drawing), but there's no UI wired up for it yet — only snags are pinnable today. The columns are there so that can be added later without another migration.
- Apartment blocks (`blocks` table) reuse the existing `quality_gates`/`handover_documents` tables rather than a parallel set of tables — both got a new nullable `block_id` alongside the (now nullable, previously required) `plot_id`, with a check constraint enforcing exactly one of the two is set per row. `plots.block_id` (nullable, `on delete cascade`) is what makes a plot a "flat" rather than a standalone house — `seed_plot_defaults()` branches on whether it's null to decide which gate/document set to seed. This was chosen over a separate `flats`/`block_gates` table structure specifically so `block-detail.html`'s gate-card and document-row rendering could reuse `plot-detail.html`'s code almost unchanged, just re-scoped to `block_id`.
- Quality gates and handover documents used to be one set per site; they're now one set per **plot** (`plots` table), created automatically whenever a plot is added. Any gates/documents that existed before this change were migrated into an auto-created "Plot 1" for their site during the schema migration, so nothing was lost — rename or re-organise that plot if it doesn't match how you actually want plots split up.
- Snag lists went through the same change: `plots` is now the single shared table behind both Plot Handovers and Snagging, and a snag list is created automatically alongside a plot's quality gates/handover docs (one list per plot, `snag_lists.plot_id`). Any pre-existing snag items from before plots existed were migrated into an auto-created "Plot 1" the same way. Deleting/renaming a plot is done from the Plot Handovers page — Snagging just links into whichever list already exists for the plot.
- Actually sending email automatically (rather than opening a pre-filled draft) would need an email-sending service (e.g. Resend) wired into a Netlify function with an API key — not set up here to keep the app dependency-free out of the box.
- Multi-account access control is enforced by Row Level Security, not client-side checks — every table's policies now check membership via a `project_members` table (through `is_project_member()`/`is_project_owner()` helper functions) instead of "any signed-in user," so even a hand-crafted API call can't reach a site you're not on. Membership is only ever granted two ways, both `security definer` so a client can't insert into `project_members` directly: automatically for whoever creates a site (a trigger), or via `join_project_by_invite()` when someone opens a valid invite link. `org_settings` (the company logo) and the `site-photos` storage bucket deliberately stay outside this — they're organisation-wide, not site-scoped, so every signed-in user keeps read/write on them same as before. **Storage isn't per-site restricted** — any signed-in user can still upload/delete under any project's photo folder if they somehow knew the path, same as before this feature; this was a deliberate scope decision, not an oversight, since reads on that bucket are already fully public (unauthenticated, keyed by an unguessable UUID filename) to support printed/PDF reports, so a member-only write policy would have added complexity without closing the read side's exposure. Tighten this later if it matters for your use case — the natural approach is `storage.foldername(name)` combined with `is_project_member()`, but the bucket has three different path shapes (`org-logo/…`, `<project_id>/…`, `drawings/<project_id>/…`) that would each need separate handling.
- When migrating an existing installation onto this feature, every user who could see a site before still can — they're added as either its owner (if `projects.created_by` matches them) or a collaborator (everyone else), once, the first time this migration runs. This is a one-time grandfather step, not an ongoing behaviour: a user who signs up afterwards does **not** get automatically added to old sites on a later `schema.sql` re-run, only to sites they create or are explicitly invited to.
- General (not-plot-specific) snag lists reuse `snag_lists.plot_id`, which was already nullable with a unique index that already tolerated multiple null rows (an artifact of the pre-migration legacy-list backfill mentioned above) — creating a second, third, etc. null-`plot_id` list on purpose needed no schema change there. The only new column is `snag_items.plot_id` (nullable, `references plots(id) on delete set null`), letting each item within a general list record its own plot independent of the list itself; deleting that plot later just clears the reference rather than deleting the snag item. No RLS changes were needed — the existing editor-only writes on `snag_lists` and fully member-level `snag_items` already produce the right permission shape (owner/collaborator creates the list, anyone including a snagging-only member can add/edit its items).
- Snagging-only is a third `project_members.role` value alongside `owner`/`collaborator`, with its own invite code column (`projects.snagging_invite_code`) and its own pair of `regenerate_snagging_invite_code()`/`revoke_snagging_invite_code()` functions — kept fully independent of the collaborator invite link so an owner never has to remember to "downgrade" someone who joined the wrong way. `is_project_editor()` (owner or collaborator, not snagging) gates every table a snagging-only member shouldn't see at all (weekly reports, quality gates, handover documents, commercial items, monthly reports, blocks, `project_members` itself, and writes to plots/drawings/snag_lists); `is_project_member()` (any role) still gates `snag_items` fully and read-only access to `plots`/`drawings`/`snag_lists`, since a snagging-only member needs those to navigate to and pin a snag. `get_my_role()` is a small security-definer function that lets a client find out its own role even on tables it otherwise can't read (`project_members` itself is editor-gated) — `project.html` uses it to decide whether to render the full site page or the cut-down snagging-only one.
- Weather auto-fill is the one place the app calls an external API directly from the browser rather than going through Supabase — `geocodePostcode`/`fetchWeatherConditions`/`conditionFromWeatherCode` in `tracker/js/app.js`. Both postcodes.io and Open-Meteo are free and keyless, so there's nothing to configure, but it does mean those two domains need to be reachable from wherever the app is used.
- H&S Audits are two tables: `hs_audits` (one row per audit, `audit_type` 'internal'/'external', gated `is_project_editor()` for every operation — this is a management feature, not exposed to snagging-only members at all) and `hs_audit_items` (one row per `HS_CHECKLIST` entry, internal audits only). `section`/`item_name` are copied onto each item as plain text at creation time rather than referencing `HS_CHECKLIST` by index, so editing that constant later never rewrites an already-completed audit's wording. `hs_audits.month` uses the same first-of-month `date` format as `monthly_reports.month`, so "does this project have an audit for month X" is one equality match; the "flag if not done this month" nudge on the site page and the monthly report roll-up both just check `month = <first of that month>` against today's/that report's month, live — there's no separate stored flag or historical "missed months" tracking, only "does the current (or that report's) month have one." A monthly report freezes a snapshot of that month's audits (score/flagged count for internal, file link for external) into its own `hs_audits` jsonb column at generation time, same convention as its other fields, so it doesn't change if an audit is edited or deleted afterwards.
- The weekly report's Clerk of Works upgrade added three new jsonb columns to `weekly_reports` — `labour_records`, `risk_items`, `statutory_milestones` — plus two fields folded into JSON shapes that already existed rather than getting columns of their own: `verification_notes` on each `progress_items` entry (Verified Quality & Works Audit) and `plot_area`/`category`/`compliance_status`/`caption` on each `photos` entry (the tagged photo gallery). The old free-text `issues_risks` column is left in place, unused by the form going forward — same "old column stays, unused" pattern as `progress_summary`/`next_week_plan`/`labour_on_site` before it — since `risk_items` replaces it as the form's structured input. Because the monthly report's "Issues / Risks / Delays" section previously only ever read that free-text field, `monthly_reports` gained its own `risk_items` jsonb column (flattened across the month's reports with each entry tagged by `week_starting`, same convention as `commercial_items`) so the monthly roll-up doesn't silently go blank once weekly reports stop populating the old field; `monthly-report-view.html` renders both — the new structured table for reports that have `risk_items`, and the legacy text section for any that only ever had `issues_risks`. `progress_items`' dedup (across a month's weekly reports, keyed by item id, keeping the highest % reached) now also carries the most recent non-blank `verification_notes` forward, so a Clerk of Works sign-off logged in an earlier week isn't lost if a later week re-logs the same item with a lower % or a blank note. Labour records and statutory milestones are **not** rolled up into the monthly report — they're kept as weekly-only, operational detail.
- `mountTableEditor()` in `tracker/js/app.js` is a small generic add/edit/delete table editor (columns: text/number/select/date, with optional badge coloring and `<datalist>` freetext suggestions) driving the Labour, Risk, and Statutory Milestones trackers on the weekly report form from one shared implementation rather than three near-duplicate ones. Every `select` column always gets an injected blank leading option even when the caller's `options` list doesn't include one — without it a `<select>` defaults to its first real option, which would make an "add a completely empty row" click silently pick up e.g. "Adequate" or "Low" instead of being ignored.
- Weekly report photos auto-raising snags needed no schema change at all — it's entirely client-side logic in `weekly-report-form.html` (`resolveSnagListId`/`syncActionRequiredSnags`) reusing the existing `snag_lists`/`snag_items` tables and RLS exactly as they already stood, plus two new keys (`snag_item_id`, `snag_list_id`) folded into each `photos` entry, the same "add fields to an existing jsonb shape" pattern used throughout this feature. Plot matching uses `normalisePlotToken()` (now exported from `tracker/js/app.js`) — the same digit-extraction matching `suggestPlotProgress()`/`syncGateStatusFromMilestones()` already use for progress-item plot tags — rather than an exact string match; an earlier version used exact matching, which was strict enough that a phone-typed tag or a bare "1" instead of "Plot 1" would silently miss a real plot and fall through to the general list. An apartment block's own name still never matches, since a block has no snag list of its own, only its flats (which, being plots under the hood, match normally). The general-list fallback (title `"Weekly Report Issues"`, `plot_id` null) is get-or-created by a case-insensitive title lookup scoped to `plot_id is null` on that project, so it's reused indefinitely rather than spawning a new list on every report; a plain client-side select-then-insert like this could in principle race under concurrent saves, same as every other get-or-create in this app (e.g. general snag list creation itself) — accepted for the same reason: one site is normally administered by one person at a time. `syncActionRequiredSnags()` re-resolves and re-syncs every Action-Required photo on **every** save, not just the first time — a photo that already has a `snag_item_id` gets its `location`/`description` refreshed from the photo's current category/caption, and is *moved* (its `snag_list_id` updated) if the resolved list has changed since it was raised, rather than being frozen at whatever list it first landed on. This matters in practice: a site manager who types a quick "1" while out on site, saves, then goes back later and tidies the tag to "Plot 1" expects the snag to end up on Plot 1's list, not stuck wherever the first save put it.
